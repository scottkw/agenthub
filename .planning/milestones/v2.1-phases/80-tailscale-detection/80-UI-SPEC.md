### New — Health modal stepped checklist (D-05 from CONTEXT.md)

A 4-row checklist rendered inside the existing Tailscale Status field-group or in a collapsible `<details>` block (see Interaction Contract below).

```
[ step-1 ] Binary detected          ← green if pass, red if fail
[ step-2 ] Daemon running            ← green/amber if pass, gray if step-1 failed
[ step-3 ] Connected to Tailscale    ← green/amber if pass, gray if step-2 failed
[ step-4 ] TLS certificates ready    ← green if pass, gray if step-3 failed
```

Styling follows `.settings-panel__check` pattern:
- Pass: `#9ece6a` checkmark icon (or filled dot)
- Fail: `#f7768e` × icon
- Warn/partial: `#f59e0b` warning icon
- Grayed out: color `#414868`, not rendered as interactive

No new CSS classes introduced for this pattern — compose from `.ts-status__dot` (8×8 dot), `.settings-panel__label`, and `.settings-panel__description` existing rules.

## Interaction Contract

### Tailscale Status section in Settings > Web Server

**Current behavior:** Single `ts-status` row with dot + text + one-line description.

**Phase 80 behavior:**

1. Dot + status text row: unchanged in structure, updated to 4 states.
2. Below the status text: a single-line description matching the state.
3. On states other than "Connected": a collapsible `<details>` element with class `settings-panel__details` expands to show the 4-step checklist. Summary label: "Show diagnostics".
4. First failing step shows platform-specific instruction text (from D-06). Steps after the first failure render in muted color (`#414868`) with no action.
5. No action buttons in the checklist — text instructions only (D-06 from CONTEXT.md).

**State descriptions:**

| State | Description text |
|-------|-----------------|
| Not Installed | "Not detected — install from tailscale.com" |
| Daemon Stopped | "Installed but daemon is not running — start Tailscale from your {platform}" |
| Running — not connected | "Daemon running but not connected to a Tailscale network" |
| Connected | "Connected via {domain or ip}" |

**Platform instruction text (shown in checklist at failing step, D-06):**

| Platform | Daemon stopped instruction |
|----------|--------------------------|
| macOS | "Open Tailscale from Applications or the menu bar" |
| Linux | "Run: sudo systemctl start tailscaled" |
| Windows | "Open Tailscale from the Start menu or system tray" |

The platform is known at build time / runtime via Go backend — the frontend receives a string field in `TailscaleHealth` (e.g. `platformHint: string`) or infers from connection state messages.

### Tailscale Path Override in Settings > Paths

Follows the Phase 79 browse button pattern exactly (already implemented in `SettingsTab.tsx`):
- The existing `tailscale` row in the Paths table (when Tailscale is not in detected CLIs) already has a Browse button and path input.
- No new UX needed — Phase 80 backend changes will surface this path to the detection logic.
- If Tailscale is in the detected CLIs list (auto-detected), the row renders as part of the CLIs table with Browse button — same as any other CLI.

### Health polling

The existing 10-second `startHealthPoller()` in `app.go` automatically propagates new `TailscaleHealth` fields (including `DaemonUp`) to the frontend via the `tailscale:health` event. No frontend polling changes required.
