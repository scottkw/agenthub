<objective>
Close the v3.4 web-share parity gap flagged in `120-VERIFICATION.md` (Human Verification #2). The /app/ route already serves the React bundle and the API enforces capability gating end-to-end — but `App.tsx` is Wails-coupled (always calls `GetRelayPort()` / `GetWebServerMode()` / `ListSessions()` and uses `fbBaseURL = http://127.0.0.1:${relayPort}`), so loading /app/ in a regular browser produces a non-functional shell.

This plan introduces an app-level mode detection module and refactors the file browser tab opener to honor the mode. In web mode, fbBaseURL becomes `window.location.origin` (same-origin), `capToken` is sourced from `?cap=` URL param, and the initial tab is opened from `?session=` URL param — no Wails RPC required. Desktop mode keeps its existing behavior bit-for-bit.

The Playwright merge gate is extended with DOM-level cells that actually mount the React shell through /app/ (one with owner cap, one with viewer cap), proving the URL-param-driven session/cap binding works under all three browser projects.

Purpose: Cross-surface parity (GUI/web) is release-blocking per the project memory note. Web-share viewers must get the same file-browser tab experience as the desktop GUI in v3.4 — not deferred to v3.5.

Output:
- `frontend/src/lib/webMode.ts` + tests — single source of truth for mode detection.
- `frontend/src/App.tsx` — mode-aware Wails RPC gating and file-browser tab opener.
- `cmd/playwright-fixture/main.go` + `global-setup.ts` — fixture serves the React bundle so DOM-level e2e tests can mount the tree.
- `frontend/e2e/files-browser.spec.ts` — scenarios 13 + 14 covering owner-cap and viewer-cap DOM paths.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-120-06-01 | Tampering | `?session=` URL param | mitigate | Treated as opaque session id; passed verbatim to /api/files/list. Server is authoritative — unknown ids return 404 (already verified by scenario 12 + Plan 04 sandbox). No client-side trust granted to the value. |
| T-120-06-02 | Information Disclosure | `?cap=` URL param in browser history | accept | The cap token already appears in URL params for /api/files/* (existing UI-09 image src pattern); this plan does not increase exposure. Capability tokens are scoped (no files.read in viewer caps) and revocable; documented in research/PITFALLS.md. |
| T-120-06-03 | Spoofing | Web-mode detection (pathname /app/) | accept | An attacker controlling the URL can flip the app into "web mode," but this only causes the React SPA to read URL params instead of calling Wails RPCs — Wails RPCs are unreachable from a browser anyway. No privilege escalation possible. |
| T-120-06-04 | Denial of Service | Empty `?cap=` URL param | mitigate | `readWebModeParams` returns `capToken: null` for missing/empty; FilesApiClient with no cap token receives 401/403 from the capability middleware → useFilesCapability resolves to 'denied' → PermissionDeniedTakeover renders. Graceful degradation, no crash. |
| T-120-06-05 | Elevation of Privilege | Viewer cap used in URL → ?cap=<owner-cap> swap | mitigate | All capability enforcement happens server-side (Plan 04 requireFilesRead middleware). The client cannot grant itself files.read by changing URL state — the server validates the signed token against the perms claim. |
