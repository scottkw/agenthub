Pitfall 7 (RESEARCH §Common Pitfalls): the `Server` struct does not know its own port — the listener is owned by `daemon/api.go:137`. Recommended solution is option (a): derive the port inside `handleSession` from `r.Host`. This is reflective, matches the `ws.BaseURL()`-based webserver pattern, and avoids adding a constructor parameter.

Library semantics recap (github.com/coder/websocket v1.8.14, accept.go:228-264):
- `OriginPatterns` matches `u.Scheme+"://"+u.Host` when the pattern contains `"://"`.
- Library short-circuits ACCEPT if Origin is empty (loopback clients dialling without Origin will pass — this is fine for non-browser localhost clients).
- Library auto-passes when `Origin == Host`.

Example r.Host values during tests: httptest.Server URLs are `http://127.0.0.1:<port>`; so `r.Host` in handleSession will be `127.0.0.1:<port>`. `dialWS` uses `ws://127.0.0.1:<port>` which the library auto-sets Origin to match Host (library behavior). So the default dialWS flow is already "same-Host" and library auto-passes even without OriginPatterns — the explicit list is belt-and-suspenders + future-proofing.

```go
// loopbackOriginPatterns returns the 4-element allowlist of loopback
// origin patterns for the given host (from r.Host). If host cannot be
// split into host:port, returns nil — letting the library fall back to
// its same-Host default, which is still loopback-safe given the
// daemon-side bind to 127.0.0.1.
//
// CONTEXT D-09: schemes included because the relay may be fronted by
// TLS in a future deployment; both "localhost" and "127.0.0.1" included
// because browsers and tools emit either form.
func loopbackOriginPatterns(host string) []string {
	_, port, err := net.SplitHostPort(host)
	if err != nil || port == "" {
		return nil
	}
	return []string{
		"http://localhost:" + port,
		"http://127.0.0.1:" + port,
		"https://localhost:" + port,
		"https://127.0.0.1:" + port,
	}
}
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Loopback client <-> relay | Relay listener is bound to `127.0.0.1:0` by `daemon/api.go:137`; all traffic is loopback in normal operation. A non-loopback client cannot reach this interface today. |
| Library-layer Origin check | `websocket.AcceptOptions.OriginPatterns` is the sole Origin gate here (no separate HTTP middleware — the relay is loopback-only and does not justify the middleware-layer defense the webserver uses). |
| Future listener rebind | If someone later rebinds the relay to `0.0.0.0` or a tailnet address, the allowlist must trigger conscious reconsideration. This is exactly the landmine-avoidance design goal (CONTEXT D-08). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-88-10 | Tampering | Future maintainer silently reintroduces `InsecureSkipVerify: true` | mitigate | Source-grep regression test `TestSecurity_NoInsecureSkipVerifyInRelay` reads `server.go` and fails on the literal (D-13 item 2; Task 1). |
| T-88-11 | Elevation | Future rebind of relay listener to non-loopback address inherits accept-all Origin | mitigate | `InsecureSkipVerify: true` replaced with loopback-only `OriginPatterns` (D-09). After the rebind a cross-origin request would be rejected by the library because the new listener's port would match the loopback pattern but the new non-loopback Origin wouldn't. The maintainer must consciously extend the allowlist — friction = good. |
| T-88-12 | Spoofing | Cross-site browser attempts WebSocket upgrade against a rebound relay | mitigate | Library-layer `OriginPatterns` match rejects any non-`{http,https}://{localhost,127.0.0.1}:<port>` Origin. Integration test `TestServer_CrossSiteOriginRejected` proves this on the loopback-only shape. |
| T-88-13 | Tampering | Port mismatch between listener and allowlist (e.g. if allowlist were hardcoded) | mitigate | `loopbackOriginPatterns(r.Host)` derives the port from each request's `Host` header (RESEARCH Pitfall 7 option a). The listener's actual port is what the dialer sees, so the port always matches in practice. |
| T-88-14 | Denial of Service | Malformed `Host` header (no port) could fail-open | mitigate | `net.SplitHostPort` error returns `nil` allowlist, which falls back to library's same-Host default. On loopback that's still `127.0.0.1`-same-Host, so safe. Unit test `TestLoopbackOriginPatterns_DerivesPortFromHost` covers empty and malformed inputs. |
| T-88-15 | Information Disclosure | Library returns a differentiated Origin rejection body | accept | The relay is loopback-only — the only reachable caller is a local process. The library's `"request Origin %q is not authorized for Host %q"` body text is acceptable residual risk (not user-facing over the network). D-14: no logs / no metrics. |

**Residual risks / deferred items:**
- Relay exposure hardening beyond Origin (capability checks, Basic Auth) deferred per CONTEXT "Deferred Ideas". Only becomes required if the relay is ever bound to a non-loopback address in a future phase.
- Differentiated library-layer error body (T-88-15) — accepted residual. The relay is not exposed to a network attacker by design; mitigating this would require a custom middleware layer not justified for a loopback-only listener.
- Non-browser loopback clients (curl, native tools) that omit `Origin` — library silently accepts missing Origin. This is INTENDED: the relay is the designated path for non-browser local clients (CONTEXT "Missing-Origin Policy" / D-05 rationale). The tailnet-facing webserver path is where missing-Origin is rejected.
