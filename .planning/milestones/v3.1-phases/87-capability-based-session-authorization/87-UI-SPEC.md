## Surface Map: New UI Components

All five UI surfaces introduced in Phase 87, with their exact placement and constraints.

### Surface 1 — Per-Session Share Panel (GUI, in `DaemonManagerPanel`)

**Location:** Within each session row in `frontend/src/components/DaemonManagerPanel.tsx`, visible only when web serving is enabled for that session (i.e., `webEnabled[sessionId] === true`).

**Trigger:** The existing "Enable" / "Disable" web serving toggle on the session row. When toggled ON, the daemon now issues two capability URLs (D-06, D-07). The share panel appears below (or inline with) the session row.

**Primary visual anchor:** The capability URL text rendered in accent `#7aa2f7` is the primary visual anchor in this panel, visually dominant over the "Read-Only Link" / "Full Access Link" labels (which are rendered in subdued `#a9b1d6`). This hierarchy guides the user's eye to the shareable artifact immediately.

**Layout:** Two equal-weight link rows. Each row contains:
- A label: "Read-Only Link" or "Full Access Link" (weight 600, 13px, `#a9b1d6`)
- A truncated URL (flex-1, `#7aa2f7`, ellipsis overflow)
- Three action buttons in a row: "Copy", "Open", "QR"
  - Button style: `.daemon-panel__btn` variant (4px 10px padding, 11px font, border `#292e42`)
  - "Copy" transitions to "Copied!" in `#9ece6a` for 1500ms, then reverts (matches existing pattern)
  - "Open" opens the capability URL in the system browser
  - "QR" toggles a QR code image below the row (200×200px, matching `.settings-web-server__qr`)

**QR behavior:** QR codes encode the join-code exchange URL (`https://host/join?code=A7K-4P2N`), NOT the capability token directly (D-09). Each link (read-only, full access) has its own QR. QR images appear inline below the link row when "QR" is active; only one QR visible at a time per session row.

**Empty / not-yet-enabled state:** No share panel visible. The existing "Enable" button is the only affordance. No auto-share (D-06 removes auto-enable).

**CSS block:** `.session-share-panel` (new BEM block). Inner elements:
- `.session-share-panel__link-row` — flex row, align-items center, gap 8px, padding 8px 0
- `.session-share-panel__label` — 13px, 600 weight, `#a9b1d6`, min-width 120px, flex-shrink 0
- `.session-share-panel__url` — flex 1, 12px, `#7aa2f7`, overflow hidden, text-overflow ellipsis
- `.session-share-panel__actions` — flex row, gap 4px, flex-shrink 0
- `.session-share-panel__qr` — display block, margin-top 8px, margin-left 128px (aligns under URL), 200×200px, border-radius 8px

- Error state (if RPC fails): `.settings-panel__error` below the button

**Confirmation dialog:** A native-style confirmation modal (matching `.quit-modal` pattern) triggered by the "Regenerate Signing Key" button click. NOT a browser `confirm()`.

**Loading state:** After the user clicks "Invalidate All Links", the button label changes to "Invalidating…" and both footer buttons are disabled until the RPC resolves. On success, the modal closes. On failure, an inline error appears above the footer buttons.

**CSS additions needed:**

### Surface 5 — Capability Error States (terminal page, HTTP errors)

These are HTTP-level error responses served by `http.Error(w, msg, code)` for WebSocket upgrade failures. The terminal page (`web/terminal.html` or equivalent) must handle three distinct capability-related failure modes in a user-facing way.

The existing `web/dashboard.html` has no error-state handling — Phase 87 defines it here.

#### Error A — Missing / malformed capability (HTTP 401)
Server message (text): "capability required"
Terminal page behavior: Show an inline error banner above the terminal iframe/container (or replace the terminal entirely if the connection fails before the WS opens):
- Text: "Access Denied — A valid share link is required to view this session. Ask the session owner to share their link with you."
- Style: red left-border banner matching `.ct-disclosure` pattern, border-left `#f7768e`, background `#16161e`

#### Error B — Capability bound to a different session (HTTP 403)
Server message (text): "capability does not match session"
Terminal page behavior:
- Text: "Wrong Session — This link is for a different session. Make sure you are using the correct link."
- Same red banner style.

#### Error C — Write attempt with read-only capability (HTTP 403, relay-level)
This is not a page-level error — it is a silent server-side drop of `MsgInput` frames. The terminal HTML page should suppress the input caret when the capability `perms` is `"read"`.

**Caret suppression mechanism (D-23):** The terminal HTML page reads the `perms` field from the session info endpoint (`GET /api/sessions/{id}/info?cap=<token>`). If `perms === "read"`, the page:
- Sets `xterm` option `disableStdin: true` (if using xterm.js) so the cursor is hidden and keyboard input is not captured
- Shows a read-only badge in the terminal status bar: "READ ONLY" — style matching `.tab-status-bar__state--on` (11px, uppercase, 600 weight, letter-spacing 0.05em), color `#a9b1d6` (muted, not accent — it is an informational state, not interactive)

The `?readonly=1` query parameter is removed as a mechanism (D-23). Read-only state is determined exclusively from the capability `perms` claim via the session info fetch.

## Interaction Contracts

### Per-Session Share Panel

| Interaction | Trigger | Outcome |
|-------------|---------|---------|
| Enable web serving | Click "Enable" on session row | Daemon issues two capabilities; share panel appears with Read-Only Link and Full Access Link rows |
| Disable web serving | Click "Disable" on session row | Share panel disappears; both URLs removed from state; grant list cleared server-side (D-15) |
| Copy a link | Click "Copy" on either row | Capability URL copied to clipboard; button shows "Copied!" for 1500ms |
| Open a link | Click "Open" on either row | `BrowserOpenURL(capURL)` — opens in system browser |
| Toggle QR | Click "QR" on either row | Fetches QR for the join-code exchange URL; displays 200×200px below the link row; "QR" label becomes "Hide QR"; clicking again hides it. Only one QR visible per session at a time. |

### Regenerate Signing Key

| Interaction | Trigger | Outcome |
|-------------|---------|---------|
| Open confirmation | Click "Regenerate Signing Key" | Confirmation modal opens |
| Dismiss | Click "Keep Links" in modal | Modal closes; no RPC fired |
| Dismiss via keyboard | Escape | Modal closes (same as "Keep Links") |
| Confirm | Click "Invalidate All Links" | Both buttons disabled; label → "Invalidating…"; RPC fires; on success modal closes; on failure error shown in modal |

### Join Code Input (dashboard + join page)

| Interaction | Trigger | Outcome |
|-------------|---------|---------|
| Type a character | Keypress in code input | Auto-uppercase; insert dash after 4th char; reject non-base32 chars |
| Submit | Click "Join Session" or Enter | Navigate to `/join?code=<value>` |
| Paste | Paste event | Auto-format pasted value (strip dashes, reformat as XXXX-XXXX, uppercase) |

### Terminal Page Read-Only Enforcement

| Interaction | Trigger | Outcome |
|-------------|---------|---------|
| Page load with read-only cap | Fetch `/api/sessions/{id}/info?cap=<token>` returns `perms: "read"` | xterm `disableStdin: true`; "READ ONLY" badge shown in status bar |
| Page load with read-write cap | perms: "read,write" | Normal terminal behavior; no badge |
| MsgInput sent against read-only cap | Relay receives frame | Server drops frame silently (no user-visible error in the terminal) |
