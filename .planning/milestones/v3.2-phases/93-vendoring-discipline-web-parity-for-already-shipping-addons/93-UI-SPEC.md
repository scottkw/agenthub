# Phase 93 — UI Design Contract

> Visual and interaction contract for the **Vendoring Discipline + Web Parity for Already-Shipping Addons** phase. This phase activates the Plugin Settings pipeline shipped in Phase 92: WebGL and Unicode 11 toggles become live; OSC 52 clipboard is wired; vendored web addons render at parity with desktop; a one-shot WebGL context-loss toast appears in the existing `.banner-stack`. Phase 93 introduces ZERO new design tokens — every visual surface composes from Phase 92's locked design system. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Phase Scope (read this first)

**In scope (Phase 93) — visual/interaction surfaces:**

1. **Live WebGL toggle behavior** — the existing Phase 92 WebGL row's toggle now hot-swaps the renderer across all open desktop terminals on Save. No new chrome — only the *behavior* of the existing row changes. Visual surface: unchanged. (WGL-01)
2. **Unicode 11 inline italic caption** — a new `<p>` directly under the Unicode 11 toggle row reading exactly: `Applies to new sessions you create.` Italicized via `font-style: italic`. Reuses existing `.settings-panel__description` color (`#9aa5ce`) and 12px size — adds only one new modifier rule (or inline style) to make it italic. (U11-01)
3. **WebGL context-loss recovery toast** — a one-shot banner injected into the existing `.banner-stack` (Phase 81 BAN-01/BAN-02 vocabulary) when the WebGL renderer falls back to DOM. Single appearance per session; user-dismissible; auto-dismisses after 8 seconds. Tone: **info** (not warning) — recovery already happened, scrollback intact, this is informational. (WGL-02)
4. **Software-rasterized WebGL preemption notice** — when SwiftShader/llvmpipe/ANGLE-software is detected at startup AND the user has WebGL enabled in settings, a one-shot banner-stack toast appears (same visual treatment as #3 above) explaining the DOM renderer is being used for performance. Persists until dismissed; does not auto-dismiss (rare event, worth keeping visible until acknowledged). Suppressed if user has WebGL OFF in settings (no notice needed). (WGL-03)
5. **Web-served terminal page parity** — the `web/terminal.html` page renders WebGL/Unicode11/OSC52-clipboard from same-origin vendored assets under `web/vendor/xterm/addons/`. **Visual treatment matches the desktop terminal exactly** — same TokyoNight palette, same monospace font, same scrollback layout. The web terminal page chrome (StatusBar at bottom from Phase 39) is unchanged. Context-loss toast on web uses the same `.banner-stack` vocabulary as desktop — implementation may be a minimal in-page banner div since the web page does not own the full React app, but the visual treatment must be indistinguishable from a desktop banner. (WGL-04, U11-02, CLIP-01, WEB-01)
6. **Web plugin-config live update** — when `/api/plugin-config` pushes a hot-swappable plugin change, web clients reflect the change with **no UI affordance** for the transition. Hot-swap is meant to feel seamless. The only visible artifact is the renderer/feature changing under the user's eyes; no spinner, no toast. Exception: WebGL toggle OFF→ON failure (e.g. context creation refused on web) reuses the same context-loss toast vocabulary from #3. (PLUG-04, WEB-03)

**Explicitly NOT in scope for Phase 93 (deferred to Phase 99):**

- Per-plugin BannerStack confirmation toasts on Unicode 11 toggle save ("Open a new session to see Unicode 11 changes") — Phase 99 / PUI-02
- Per-plugin advanced `<details>` disclosures (Search regex, Web-Links modifier, Image storageLimit) — Phase 99 / PUI-03
- New layout sections, modals, or chrome surfaces beyond the toast injections described above

**Anti-goals:**

- No "applies to new sessions" caption beneath Unicode 11 should ALSO surface a post-Save BannerStack toast in this phase — that affordance is reserved for Phase 99 (PUI-02). The italic caption alone is the Phase 93 affordance.
- No retry button, no "use WebGL anyway" override on the software-rasterized WebGL toast. Decision is final until user toggles in Settings.
- No auto-retry loop on WebGL context loss. One fall, one toast, done. (Explicit ROADMAP success criteria.)

## Copywriting Contract

### Unicode 11 italic caption

| Element | Copy |
|---------|------|
| Unicode 11 caption (`<p class="settings-panel__description settings-panel__description--italic">`) | `Applies to new sessions you create.` |

**Rules:**
- Verbatim copy locked by ROADMAP success criterion #1 ("inline italic caption 'Applies to new sessions you create'") and REQUIREMENTS U11-01 ("clearly marked as 'applies to new sessions you create'").
- Final period included (matches the period convention in the per-plugin descriptions from Phase 92).
- Sentence case (not Title Case) — matches `.settings-panel__description` precedent.
- Plain English, no jargon, no exclamation point.

**Placement:** directly under the Unicode 11 row's existing description (`Correct cell widths for emoji and CJK characters using the Unicode 11 width tables.`), separated visually only by the natural line break — no extra margin between the two `<p>` elements (use a single 0px gap; the parent `.settings-panel__field-group { margin-bottom: 16px }` separates the next plugin row).

### Context-loss recovery toast

| Element | Copy |
|---------|------|
| Toast message | `Hardware-accelerated rendering recovered — your terminal is now using the standard renderer. Scrollback is intact.` |
| Dismiss button (aria-label) | `Dismiss notification` |
| Dismiss button (visible) | `×` (XMarkIcon, 16px, on desktop; on web, an inline `×` Unicode character or minimal SVG) |

**Rules:**
- "Hardware-accelerated rendering recovered" — uses "recovered" rather than "lost" to lead with the resolution. The user experienced no data loss; lead with that.
- "your terminal is now using the standard renderer" — concrete, present-tense; says what's happening, not what failed.
- "Scrollback is intact." — addresses the most likely user concern explicitly.
- Sentence ends with a period.
- Length stays under ~120 chars to fit the existing 53px banner row visually with reasonable line wrap on a 600px-wide terminal panel.

### Software-rasterized WebGL preemption toast

| Element | Copy |
|---------|------|
| Toast message | `Hardware acceleration is unavailable on this device. Your terminal is using the standard renderer for the best experience.` |
| Dismiss button (aria-label) | `Dismiss notification` |
| Dismiss button (visible) | `×` (XMarkIcon, 16px) |

**Rules:**
- "Hardware acceleration is unavailable" — neutral, not blame-coded ("your GPU is broken" would be wrong tone for SwiftShader/iPad Safari).
- "for the best experience" — implies the choice is intentional and helpful, not a fallback.
- Does NOT mention "SwiftShader", "llvmpipe", "ANGLE", "software rasterizer", or any internal-detection vocabulary — the user does not need to know which detector triggered.
- Does NOT offer a "Use WebGL anyway" override — explicit non-goal of this phase. User can flip the WebGL toggle in Settings if they want.

### Web plugin-config live update

**No copy.** Hot-swap is silent by design (success criterion #6: "no UI affordance for the transition"). Failure case (rare — context creation refused) reuses the context-loss toast copy above.

### Error state copy

Inherited from Phase 92 — no new error copy in Phase 93. The existing patterns:

| Element | Copy |
|---------|------|
| Save error (load fail) | `Could not load plugin settings — {message}` |
| Save error (save fail) | `Could not save plugin settings — {message}` |

If `/api/plugin-config` fails on the web side (returns 401/403/500), the web terminal page MUST NOT surface a toast — failure is handled by the daemon-side capability-token middleware (returns 401 → page reload → re-auth). This is consistent with the v3.1 SEC-* model: capability failures are handled at the network layer, not surfaced as in-page errors.

### Destructive actions

**None in this phase.** Toggling WebGL, Unicode 11, or Clipboard on or off does not delete data, does not require confirmation, and does not surface a destructive modal.

### Banner placement in `.banner-stack`

`.banner-stack` already houses `LocalNetworkBanner` (Phase 60) and `UpdateBanner` (Phase 51) in App.tsx (line 749 area). The Phase 93 `WebGLRecoveryBanner` MUST render **after** UpdateBanner in DOM order so that:

1. The most recent banner (typically the recovery toast — appears in response to a runtime event) sits visually below the more persistent banners (LocalNetworkBanner / UpdateBanner).
2. The 3×53px max-height overflow scrolling logic is preserved (Phase 81 contract).
3. If both context-loss AND software-WebGL toasts fire, only one is shown at a time — software-WebGL is detected at startup (fires once, persists), context-loss fires at runtime (also persists once dismissed). They're mutually exclusive in practice (software-WebGL preemption means WebGL never started, so it can't lose context), so single-slot dispatch is sufficient.

### Web terminal page banner

The web page does not host React. Toast injection there is a single CSS-styled `<div id="webgl-recovery-banner">` element that the web JS bundle shows/hides via `style.display`. Visual treatment must match the desktop banner pixel-for-pixel:

- 53px tall, full-width above the terminal scrollback area
- TokyoNight palette tokens replicated directly in `web/assets/terminal.css`
- No animation library — same CSS transition as `.banner-exit` (`opacity 150ms, max-height 200ms`)
- Dismiss button is a plain `<button>` styled to look like the desktop dismiss button

This is the load-bearing parity assertion: **a screenshot of the web terminal context-loss toast and a screenshot of the desktop terminal context-loss toast should be visually indistinguishable** (modulo browser-chrome surrounding the canvas).

## Interaction Contract

### WebGL toggle hot-swap (live)

- User toggles WebGL OFF → presses `Save Plugins` → daemon persists → `settings:plugins` event fires.
- App.tsx's existing EventsOn subscription updates `pluginConfig` state.
- `pluginConfig` prop change cascades into every open `<TerminalPanel>`.
- Each TerminalPanel's addon-load useEffect runs: detects WebGL flipped from true→false, calls `webglAddon.dispose()`, removes from xterm instance, terminal continues rendering via DOM. **No flicker, no reflow, no scrollback loss.**
- User toggles WebGL ON → reverse: instantiate `WebglAddon`, attach, terminal continues rendering via WebGL.
- Visual feedback during the hot-swap: **none** — the switch is meant to be invisible. Users perceive the renderer change only through frame-rate / aliasing differences, not via a UI affordance.

### Unicode 11 toggle (next-session)

- User toggles Unicode 11 → presses `Save Plugins` → daemon persists → `settings:plugins` event fires.
- App.tsx state updates; pluginConfig prop cascades.
- TerminalPanel's addon-load useEffect detects Unicode 11 changed BUT does not act on already-open terminals (re-flowing the buffer would corrupt scrollback).
- The italic caption `Applies to new sessions you create.` provides the user with the affordance — no additional toast or modal in this phase.
- New sessions created after the toggle inherit the new value at session-start time.

**Decision rationale:** the italic caption alone suffices as the user-facing affordance in this phase. The post-Save BannerStack confirmation toast ("Open a new session to see Unicode 11 changes") is reserved for Phase 99 / PUI-02 — adding it now would duplicate the affordance and create design drift between Phases 93 and 99.

### Clipboard (OSC 52) toggle (live)

- User toggles Clipboard → Save → event fires → pluginConfig prop cascades.
- TerminalPanel's addon-load useEffect adds/removes ClipboardAddon live. No visual feedback — clipboard activity is by definition out-of-band.

### WebGL context loss → DOM fallback

1. Context loss event fires (sleep/wake, GPU crash, iPad backgrounding, DevTools `WEBGL_lose_context.loseContext()`).
2. TerminalPanel disposes the WebGL addon and falls back to DOM renderer. **Scrollback is preserved** (xterm core retains the buffer; only the renderer changes).
3. **No auto-retry loop** — TerminalPanel does NOT attempt to reinstate WebGL. User must explicitly toggle WebGL OFF→ON in Settings to retry (which goes through the hot-swap path, which can fail again — that's their choice).
4. TerminalPanel fires a `onWebGLContextLost` callback up to App.tsx.
5. App.tsx renders `WebGLRecoveryBanner` inside `.banner-stack` with the recovery toast copy.
6. Toast auto-dismisses after 8 seconds OR the user clicks the dismiss button.
7. **Once dismissed (auto or manual), the toast does not re-appear in the same session** — only one notification per session, even if context loss fires multiple times. (Re-firing would be noise; the recovery is the same regardless of frequency.)
8. On full app restart, the one-shot counter resets.

### Software-rasterized WebGL preemption at startup

1. App.tsx (or TerminalPanel mount) detects software-rasterized WebGL via `gl.getParameter(gl.RENDERER)` matching SwiftShader/llvmpipe/ANGLE-software/iPad Safari heuristics.
2. If detected AND `pluginConfig.webgl === true`: instantiate DOM renderer instead of WebGL; render `WebGLRecoveryBanner` with the software-preemption copy.
3. If detected AND `pluginConfig.webgl === false`: no detection action needed (user already opted out); no toast.
4. Toast persists until the user dismisses it (no auto-dismiss — startup state is rare enough to keep visible).
5. Same one-shot-per-session rule as context loss.

### Web plugin-config live update

1. `/api/plugin-config` endpoint changes (admin saves on desktop; daemon broadcasts to web clients via SSE/poll/WebSocket — implementation detail, not UI).
2. Web client reads new config; re-runs its addon-load logic.
3. Hot-swappable plugins (WebGL/Clipboard) swap silently. **No UI feedback.**
4. Non-hot-swappable plugins (Unicode 11) are flagged for next-session — but the web client does not surface this; the caption already lives in the desktop Settings UI, and the desktop user is the one making the change. The web user simply experiences the new behavior on next session.

### Reduced motion

- `WebGLRecoveryBanner` enter/exit transition (150ms opacity / 200ms max-height) MUST respect `prefers-reduced-motion: reduce` — fall back to instant show/hide (no transition).
- All other Phase 93 surfaces have no animation.

## Acceptance Snapshot (what the Phase 93 implementation looks like when done)

A returning v3.2 (post-Phase-92) user opens the app and:

1. Existing Plugins section in Settings looks IDENTICAL to Phase 92 — eight toggle rows, descriptions, three-state Save button — with **one** visible addition: under Unicode 11's existing description, an italic line reads `Applies to new sessions you create.`

3. Toggling Unicode 11 OFF/ON does NOT change open terminals (the italic caption explained why); a newly-created session inherits the new value.
4. Toggling Clipboard does not surface any UI change; OSC 52 sequences from CLIs now do (or no longer do) hit the system clipboard.
5. Scrollback is intact.` Toast auto-dismisses after 8 seconds; never re-appears in the same session.
6. Your terminal is using the standard renderer for the best experience.` Toast persists until dismissed; never re-appears in the same session.
7. Opening the web terminal page over Tailscale: scrollback, font, palette, and StatusBar are visually indistinguishable from the desktop terminal. DevTools Network tab shows zero requests to any non-`self` origin (CSP `script-src 'self'` honored). When the desktop user toggles WebGL on the web page is consuming, the renderer hot-swaps under the user's eyes with no in-page UI feedback.
8. CI: pushing a PR that bumps `frontend/package.json`'s `@xterm/addon-clipboard` version without updating `web/vendor/xterm/VERSION` causes the generalized `vendor_drift_test.go` to fail red. (Not a UI surface, but the load-bearing CI gate that protects all of the above.)
