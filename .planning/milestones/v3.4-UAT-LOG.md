### Open Item #1 — Share UI mints viewer cap without `files.read`

**Discovered:** During UAT #2 (web viewer test attempt)

**Symptom:** Opening the share URL (from Sessions tab in the dev build,
form `/sessions/<id>?cap=<token>`) and converting it to `/app/?session=<id>&cap=<token>`
loads the React app correctly (web-mode detection works) but the file browser
tab fails with "Could not load directory — Network error" because the daemon
returns 403 (missing `files.read` perm on the viewer cap).

**Per `internal/daemon/api.go:1049-1054`:**
```go
ownerPerms := "read,write"
if a.engine.filesReadEnabled() {
    ownerPerms = "read,write," + capability.PermFilesRead
}
rClaims := capability.Claims{ Perms: "read", ... }              // viewer — no files.read
wClaims := capability.Claims{ Perms: ownerPerms, ... }          // owner — has files.read when enabled
```

**This is by design per FS-12:** "web-share viewer token issuance does NOT
include `files.read` unless the share grant explicitly enables it (default
OFF for viewers)".

**The UX gap:** There is no UI in v3.4 to explicitly enable `files.read`
when minting a share grant, so in practice viewers never get file browse
access. The owner-with-files.read cap exists in the codebase but the GUI
share button doesn't surface it.

**Disposition options:**
- (A) v3.4.1 hotfix: add a checkbox to the share dialog ("Allow viewer to browse files") that flips the viewer cap's Perms to include `files.read`
- (B) v3.5 issue: defer the share UI expansion; document the limitation
- (C) Change default: make viewer caps include `files.read` by default (contradicts FS-12)

### Open Item #2 — "Enable Web" share UI still surfaces legacy `/sessions/<id>` URL

**Discovered:** During UAT #2 (web viewer test attempt)

**Symptom:** The Sessions tab share button gives users a URL of form
`https://<tailnet>:7443/sessions/<id>?cap=<token>`. This loads the
**pre-v3.4 terminal-only viewer**, not the new React app at `/app/`. As a
result, users never discover the file browser through the normal share flow.

**Disposition options:**
- (A) v3.4.1 hotfix: update share UI to surface `/app/?session=<id>&cap=<token>` URLs
- (B) v3.5 issue: defer; document that `/app/` is reachable by manual URL editing
- (C) Add both URLs (terminal-only + file-browser) in the share dialog

### Open Item #3 — Warp terminal swallows Ctrl-\

**Discovered:** During UAT #2 (TUI detach test)

**NOT an AgentHub bug** — confirmed by `cat -v` test in Warp (no bytes
reach the process) and by working Ctrl-\ in macOS Terminal.app. Likely a
recent Warp update added an OS-level handler for Ctrl-\ that doesn't show
up in Warp's keybindings panel.

**Disposition:**
- File a Warp bug report (out of AgentHub scope)
- Optionally v3.5 issue: make AgentHub's detach key configurable
