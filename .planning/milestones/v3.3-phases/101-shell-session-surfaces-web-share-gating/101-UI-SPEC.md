### Web-share security banner copy (NEW — one-time, persisted dismissal)

| Element | Copy |
|---------|------|
| Banner role | `role="alert"`, `aria-live="assertive"` (NOT polite — security warning) |
| Heading | `Web sharing this shell will expose arbitrary command execution.` |
| Body line 1 | `Anyone on your tailnet who can reach the daemon will be able to type commands as your user account.` |
| Body line 2 | `Read-only viewers cannot type, but commands you run remain visible to them.` |
| Primary CTA (right-aligned) | `Enable web sharing` |
| Secondary CTA | `Cancel` |
| Dismiss-aria-label | `Dismiss security warning` (× icon) |
| First-time vs subsequent | Banner shows on the FIRST toggle-ON for any shell session, ever. After confirming once, the user's settings.json records `shellWebShareWarned: true` and subsequent toggles act immediately. |

This matches the v3.2 Phase 96 "amendment 2" CSP-confirmation pattern (informational, persisted, non-modal).

### GUI: `DaemonManagerPanel` & `StatusBar` — web-toggle gate

**Files:** `frontend/src/components/DaemonManagerPanel.tsx`, `frontend/src/components/StatusBar.tsx`, `frontend/src/App.tsx`

**Behavior change:** When a shell session's `Web On` button is clicked AND `settings.shellWebShareWarned !== true`, the toggle action is intercepted:
1. The optimistic toggle does NOT fire `ToggleWebServing(id, true)`.
2. Instead, `App.tsx` pushes a `ShellWebShareBanner` entry into the existing banner-stack vocabulary (the same `.banner-stack` flex-column container used by `PluginToggleBanner` and `LocalNetworkBanner`).
3. The `Web On` button enters an intermediate disabled state (visual: opacity 0.5, label `Web On…`, `aria-busy="true"`) until the user resolves the banner.
4. On banner "Enable web sharing" → `App.tsx` calls `SetShellWebShareWarned(true)` (NEW Wails RPC — daemon settings.json key), then `ToggleWebServing(id, true)`.
5. On banner "Cancel" → no daemon RPC fires; toggle returns to off state (`Web On` label restored, button re-enabled).
6. On banner × → same as Cancel.

**For sessions that are NOT shells** (the 6 AI CLIs): web-toggle behavior is unchanged — the banner never appears.

**For shells AFTER the first-confirmation** (`shellWebShareWarned === true`): the toggle is immediate, no banner. The warning is one-time-per-machine, not per-session.

## Accessibility

| Requirement | How Phase 101 satisfies it |
|-------------|----------------------------|

## Edge Cases

| Case | Behavior |
|------|----------|
| No shells discovered on system (extremely rare — every modern OS ships bash/sh/pwsh) | GUI modal: no shell rows render. CLI: `new shell` errors gracefully. TUI: shell entries omitted from picker. No empty-state placeholder anywhere (silent absence pattern, matches AI CLI behavior). |
| Custom CLI path override accidentally pointing to a shell (e.g. `cliPaths["claude"] = "/bin/zsh"`) | Already mitigated by Phase 100 engine.go `knownShells` filter — stale entry is discarded on load. No UI handling needed. |
| User opens new-session modal while daemon is still starting (race) | AI CLIs cached in App.tsx render immediately. Shells: loading skeleton until ListShells resolves. If ListShells fails (daemon down), skeleton silently replaced by nothing. |
| User toggles web ON for shell session, then dismisses banner, then immediately clicks Web On again | Banner re-appears (idempotent — `shellWebShareWarned` is only set on confirm, not on dismiss). |
| User has `shellWebShareWarned === true` from a previous install, then creates a fresh shell session | Toggle is immediate, no banner. This is by design — the warning is per-user-per-machine, not per-session. |
| User clicks "Web On" for an AI CLI session (e.g., claude) with `webEnabled = false` | Unchanged behavior — optimistic toggle, no banner. The shell gating logic is gated on `cli ∈ shellSet`. |
| Multiple shell sessions exist, user has confirmed once, web server is restarted | All shells remain web-disabled (Phase 100 establishes shells override the agent-session auto-enable default — per SHELL-07). User must manually toggle each shell. No banner re-appears because already confirmed. |
| Multi-client viewing a shell session via web (after web-on enabled) | Each client's read-only / writable badge unchanged. The "arbitrary code execution" risk is communicated via the one-time banner; no per-viewer banner needed (the existing per-session-share-panel surfaces are sufficient). |
| Settings.json migration: user upgrading from v3.2 (no `shellWebShareWarned` key) | Field defaults to `false` on load — user sees the banner on first shell-web-share toggle, just like a fresh install. No schemaVersion bump (additive boolean with `omitempty`). |
| Windows pwsh.exe basename includes `.exe` | Already handled by Phase 100 (basename normalization in `knownShells` map). UI displays `Shell — PowerShell` (or `Shell — Windows PowerShell` for legacy 5.x) without `.exe`. |
| Tab agent badge for an unknown CLI string | Falls back to muted `#9aa5ce`. Tab still renders correctly. |
| Light vs Dark terminal in TUI | `lipgloss.LightDark(hasDark)` adaptive — light variant `#3d5a80` ensures 4.5:1 on `#e9e9ec`. No code paths use the dark value on light terminals. |

## Decisions Made With Rationale (autonomous run)

The user instructed "work without stopping for clarifying questions." Below is every decision I made and why, so the planner/checker/auditor can challenge any single one without re-running discovery.

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Shell badge color = `#89ddff` (slate cyan, dark) / `#3d5a80` (light) | TokyoNight palette already contains `#89ddff` (used in some xterm theme variants); distinct from existing 6 agent colors (blue, green, purple, cyan, amber, red); deuteranopia-safe distinction from the closest neighbor (gemini cyan `#2ac3de`) verified by hue+luminance gap. Slate-gray was the alternative from 101-CONTEXT.md "Specifics" §2 — rejected because gray collides visually with the existing `FgMuted` color and disabled-state styling. Terminal-green (`#10b981` Tailwind emerald) was also suggested — rejected because too close to OpenCode's `#9ece6a` (both greens). |
| 2 | Render agent badge as a new 8px dot to the left of the tab name (not as a colored tab background or border) | Existing tab visual vocabulary is "status dot + name + close". Adding a second 8px dot mirrors the pattern. Coloring the tab background per agent breaks the existing `--active` border-bottom indicator. Coloring a border-left would conflict with the existing 2px `--active` bottom border visually competing for "is this active?" signal. |
| 3 | Shell entries in modal use `Shell — <name>` prefix (not bare `bash`) | Existing AI CLI entries are "Product Name" form (`Claude Code`, `Gemini CLI`). Bare `bash` would read as a fourth AI CLI rather than a category. The em-dash prefix groups all shells visually without needing a `<hr>` divider or section header (which would over-engineer a list of 3-5 entries). |
| 4 | Shell rows render AFTER AI CLI rows in the modal (no divider) | AI CLI rows are the primary use case (AgentHub's tagline is "AI coding terminal sessions"). Putting shells below ensures the typical workflow (pick a CLI) stays at the top. Visual grouping is provided by the `Shell —` prefix; an explicit divider would be redundant. |
| 5 | Two-line agent button for shells (primary + resolved path) | The resolved path is load-bearing on Windows (`pwsh.exe` vs `powershell.exe` for v7 vs v5.x) and useful disambiguation when multiple bash binaries exist (e.g., `/bin/bash` vs `/opt/homebrew/bin/bash`). The mono-styled secondary line surfaces the path without crowding. AI CLI rows stay single-line (no path info needed). |
| 6 | Web-share confirmation is an inline banner, not a modal | The existing daemon-manager + status-bar contexts already use vertical banner stacks (`PluginToggleBanner`, `LocalNetworkBanner`, `WebGLRecoveryBanner`, `UpdateBanner`). A modal would break the established UX vocabulary and feel heavy-handed for a one-time-per-machine toggle. Inline banner with explicit Confirm/Cancel buttons preserves the established pattern. |
| 7 | Banner role=alert + aria-live=assertive (NOT polite) | The banner blocks an action (the toggle does not complete until resolved). Screen reader users MUST be alerted, not informed in passing. Differs from PluginToggleBanner (informational, polite). |
| 8 | Confirmation is one-time-per-machine (not per-session) | Matches existing AgentHub pattern of CT-disclosure-on-first-cert-provisioning (v1.2 — "one-time acknowledgment persisted as `ct_disclosed` file"). Per-session would create alert fatigue without adding security value (the user has already accepted the threat model). Persistence in `settings.json` (not localStorage) matches the 101-CONTEXT.md decision and survives reinstalls. |
| 9 | `shellWebShareWarned` is a backend-persisted boolean (settings.json) | Matches 101-CONTEXT.md decision §"Web-share confirmation persistence". Backend persistence > localStorage because: (a) survives browser-context resets (the web-served UI could theoretically also want this — though currently doesn't), (b) survives Wails build upgrades, (c) consistent with other booleans (`startMinimized`, `autoCloseSession`). |
| 10 | Banner shell-warning red accent reuses existing `#f7768e` destructive color | No new red is added. Adds 3px left-border for visual differentiation from the other (info-style) banners in the stack. |
| 11 | Banner takes top stack priority when shown | It blocks an action. Other banners are advisory. Stack priority is a render-order choice in App.tsx — no new infrastructure. |
| 12 | Focus moves to "Cancel" (safe action) when banner appears | Established pattern for destructive-but-blocking dialogs (QuitConfirmModal v3.0 Phase 85 defaults to "No" — `killFocusYes = false`). Mirror that. |
| 13 | CLI argv shape: `agenthub new shell [<path>] [--shell=X]` | Discussed in 101-CONTEXT.md §"Specifics" §4. Positional `<path>` matches existing `agenthub new <agent> <path>` shape exactly. `--shell=X` flag selects the specific shell (otherwise system default). Avoids creating a `agenthub shell` top-level command (would split mental model with `agenthub new` for AI CLIs). |
| 14 | CLI: `-- extra-args` are ignored (with stderr warning) for shells | Phase 100 RESEARCH explicitly decided `req.Args` is NOT forwarded to shells (Anti-Pattern, Assumption A6). The CLI must match. A warning (not a hard error) keeps the surface forgiving for users who muscle-memory the AI CLI pattern. |
| 15 | Shell sessions DO NOT auto-enable web sharing even when web server is running | This is SHELL-07 (the literal requirement). Implementation point: in `App.tsx` `webEnabled` seeding from daemon `SessionInfo.webEnabled`, shells will already receive `webEnabled === false` from the daemon (Phase 101 also requires the daemon to override the auto-enable default for shells — see "Open decisions deferred to planner" §3). |
| 16 | Use 2-line modal button for shells (instead of 1-line + tooltip-only path) | A tooltip would be invisible until hover — defeating the purpose of showing the resolved path during selection. The 56px row is acceptable additional vertical space (4-5 shells max, so total list growth ≤ ~120px). |
| 17 | TUI badge: extend `agentBadgeColor` with `case "shell", "bash", "zsh", "pwsh", "powershell"` | Minimal change to existing function; matches established switch-case pattern; doesn't disturb the 6 existing agent colors. |
| 18 | No new font, no new icon library, no shadcn initialization | Project has zero shadcn footprint, locked TokyoNight palette since v3.0, and a stable icon library (heroicons). Adding any of these now would be a milestone-level decision, not a phase decision. |
| 19 | TUI does NOT show resolved shell path in agent picker | TUI lines are width-constrained (sidebar + content panes). Path bloat would force ellipsis. Path can appear in the session-detail tooltip if planner finds a clean place; otherwise omitted. |
| 20 | Banner copy is locked verbatim per Phase 99 PUI-02 precedent | Locking copy at UI-SPEC time prevents the gsd-executor from "improving" the wording during implementation. Pattern proven in Phase 99 (PluginToggleBanner copy was locked and the checker enforced it). |

## Open Decisions Deferred to Planner (gsd-planner-phase)

These are NOT design decisions — they are implementation choices the planner should make when decomposing into plans.

1. **`agenthub list --shells` companion subcommand?** — Recommended in this UI-SPEC for "shell not found" error path. Planner decides whether to ship in 101 or defer to a v3.4 polish.
2. **`DetectedShell` Wails TypeScript binding shape** — handwritten or generated? Project convention is "hand-edit `wailsjs/go/main/App.{d.ts,js}`" per Phase 99 PUI-04 decision. Planner mirrors.
3. **Daemon auto-enable override for shells** — when creating a shell session, the daemon currently auto-enables web sharing (Phase 59 + 61 default). Phase 101 SHELL-07 requires the override to happen on the daemon side, not just the frontend. Planner decides whether the override lives in `engine.CreateSession` (most likely) or in the `handleListSessions` enrichment step.
4. **Banner-stack priority enforcement** — App.tsx today renders banners in array order. The new priority order (shell-warning highest) can either be implemented via sorting banner array on push, or via separate slots in the stack render. Planner picks.
5. **`agenthub:args:shell:<name>` localStorage key namespace migration** — if a user has `agenthub:args:bash` from a previous experiment, it would silently be ignored. Acceptable for v3.3; document in plan as "no migration needed."
6. **Skeleton-vs-spinner for shell-loading state** — UI-SPEC specifies a skeleton row. Planner decides whether to factor it into a reusable `<Skeleton>` component or inline it.
