## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, control button padding |
| sm | 8px | Inline gaps (tab, status-bar, modal footer gap), button padding vertical |
| md | 16px | Modal body padding, header padding horizontal, section spacing |
| lg | 24px | Modal section margin-bottom, QR modal padding |

| 2xl | 48px | Not used directly — reserved for page-level breaks |

Exceptions:
- Tab height: 42px (not a multiple of 8 — matches macOS traffic-light row height expectation)
- Status bar height: 32px (compact information density row)
- Tab close button: 16px × 16px (icon-only hit target; below 44px — desktop app, not touch)
- Tab bar button: 38px × 38px (desktop icon button, sufficient for pointer input)

Note: The existing stylesheet uses a raw 2px gap on tab bar control buttons as an internal CSS implementation detail. This value is not a planner-facing token and is not part of the spacing contract. The planner uses `xs` (4px) as the minimum gap token.

**Source:** `frontend/src/style.css` — measured from all height/padding/gap declarations.

## New UI Surface: Daemon Startup Failure

Phase 20 introduces one new visible state: the daemon fails to start within 3 seconds (EnsureDaemon timeout). Currently, `App.tsx` init() has a `catch (err)` that only `console.error`s — this is invisible to the user.

### Required: Daemon Connection Error Banner

When `init()` fails (relay port unavailable, daemon unreachable), the app must display an inline error state rather than silently showing an empty tab bar.

**Placement:** Full-width banner in the terminal container area (below the tab bar, which shows zero tabs).

**Focal point:** Left border accent (`border-left: 3px solid #f7768e`) — draws the eye to the destructive signal and anchors the banner's visual hierarchy.

**Copy (see Copywriting Contract below).**

**Visual spec:**
- Background: `#16161e` (secondary surface)
- Border-left: 3px solid `#f7768e` (destructive — same pattern as `.ct-disclosure` component)
- Border: 1px solid `#292e42`
- Border-radius: 4px
- Padding: 12px 16px
- Margin: 16px (inset from terminal container edges)
- Text: 13px, color `#a9b1d6` (text secondary)
- Button: same style as `.tab-status-bar__btn` — border 1px solid `#292e42`, background transparent, color `#a9b1d6`, hover background `#1e2030`

**Interaction:** "Retry Connection" button calls `init()` again. No automatic retry — user-initiated only.

**States:**
1. **Connecting** (transient, only shown if init takes > 500ms): Small status line in terminal container, text muted `#565f89`, "Connecting to session daemon..." — 13px, no border
2. **Error** (persistent after catch): Error banner with retry button
3. **Ready** (normal): Banner is absent; normal tab bar + terminal display

Note: The "Connecting" transient state is optional for Phase 20 — EnsureDaemon is synchronous from the frontend's perspective (Go blocks until daemon ready before returning from startup). The error state is the only mandatory new surface.

## Session Restore Interaction Contract

Phase 20 success criterion #2: "Reopening the GUI reconnects to the daemon and shows the exact same sessions that were running before close."

The `init()` function in `App.tsx` already calls `ListSessions()` and maps results to tabs. This behavior is already implemented. After Phase 20, `ListSessions()` goes to the out-of-process daemon instead of in-process engine — the frontend is unaware of this change. **No frontend interaction change required.**

The tab restoration order contract: tabs restored in the order returned by `ListSessions()`. First tab in the list becomes active. This is existing behavior (App.tsx line 88: `setActiveId(restoredTabs[0].id)`).
