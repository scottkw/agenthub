<objective>
Fix GitHub Issue #57: on Linux, a shell session's clean `exit 0` (or any natural exit) must cause the GUI tab / TUI list entry to auto-close within ~1s — matching the macOS behavior shipped in v3.3 SHELL-12. Root cause is Linux PTY-master Read blocking indefinitely after the slave-side child exits (vs. macOS surfacing io.EOF). The downstream chain (Hub.Run -> engine.go:328 natural-exit goroutine -> onExit -> Wails polling -> frontend session:exit) is already correct on Linux once the read loop unblocks.

Purpose: Close the only daemon-side blocker for the v3.3.1 PTY-01..04 release-blocking parity contract. Surgical, hermetic to `internal/pty/`. Patch-release rules — no refactors beyond the new detector + its wire-up + the test flip.

Output: A Linux-only Wait4-polling exit-detector goroutine plus a no-op stub for other platforms, wired into `NativePTYBackend.Create`. The detector caches the real exit code and closes the PTY master, which forces `Hub.Run`'s blocked Read to return an error, which unblocks the existing natural-exit goroutine. Plus the long-skipped regression test re-enabled and a cross-surface VERIFICATION.md.
</objective>

<decisions_locked>
<!-- Resolutions to RESEARCH §8 open questions. LOCKED for this plan. -->

Q1 (PID-recycle race) -> Detector owns CancelContext.
The detector calls sess.CancelContext() BEFORE closing the PTY. Rationale: Cancel triggers cmd.Cancel = Process.Kill (set by go-pty's CommandContext). Doing this BEFORE we reap via Wait4 means the kill (a no-op if child already exited) reaches the kernel while we still hold the PID. The subsequent engine.go:335 sess.CancelContext() becomes idempotent (context.CancelFunc is safe to call multiple times). Eliminates the PID-recycle window described in RESEARCH §10 Pitfall 2.

Sequencing inside the detector when Wait4 reports the child has exited:
  1. Cache exit code via sess.SetExitCode(...)
  2. Call sess.CancelContext() (kills cmd context; harmless if already exited)
  3. Acquire sess.mu, snapshot p := sess.pty, release lock
  4. _ = p.Close() — this is what unblocks Hub.Run.Read
  5. Return

Q2 (existing 100 ms sleep at engine.go:337) -> KEEP.
Patch-release rules: no refactors beyond the surgical addition. Once the detector caches the real exit code via SetExitCode BEFORE the engine goroutine wakes, that sleep becomes a defensive no-op (the -1 -> 0 fallback at engine.go:339-341 never fires for naturally-exited Linux sessions). No churn outside internal/pty/ + the test flip.

Q3 (Linux-only unit test for the detector) -> YES, add it.
File: internal/pty/exit_linux_test.go with `//go:build linux`. Covers PTY-02 mechanically (detector fires on natural exit; detector does NOT call Wait4 when IsKilled is true). Cheap, deterministic on Linux CI, doesn't run on macOS executor's box.

Build-tag split -> Pattern B (_linux.go / _other.go). Matches existing internal/pty/cleanup_windows.go ↔ cleanup.go and job_windows.go ↔ job_other.go precedent. Filenames: exit_linux.go (`//go:build linux`) and exit_other.go (`//go:build !linux`).

Poll cadence -> 100 ms, no jitter. Single named constant linuxExitPollInterval = 100 * time.Millisecond at top of exit_linux.go. Matches existing 100 ms convention at engine.go:337 and is dominated by the upstream 500 ms Wails poll latency anyway.

Wait4 source -> stdlib syscall.Wait4. Not golang.org/x/sys/unix.Wait4. The detector is in a `//go:build linux` file; stdlib is sufficient and avoids a new transitive dependency surface for a patch release.

  <behavior>

    - When Wait4 returns an error (most commonly ECHILD — already reaped), the detector returns silently — the cleanup path that did the reaping owns state transition.
    - The detector starts only if sess.cmd != nil and sess.cmd.Process != nil; otherwise it returns immediately.
    - On non-Linux platforms (`//go:build !linux`), startExitDetector is a no-op function with the same signature.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| child process -> daemon | The exited child's status is read via syscall.Wait4 — kernel-mediated, no untrusted input crosses here. |
| detector goroutine -> Session state | Goroutine writes s.exitCode and reads s.pty under s.mu — already-trusted in-process boundary. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-110-01 | Tampering | sess.exitCode (concurrent write race detector vs. killSession) | mitigate | All writes go through SetExitCode which holds s.mu. killSession path uses MarkKilled before any state change; detector checks IsKilled each tick and bails. PTY-02 coordination locked. |
| T-110-02 | Denial of Service | Wait4 detector leaks on long-lived sessions or never-exiting children | mitigate | Detector exits when sess.IsKilled() is true (covers Kill path). On natural exit, detector exits after one successful Wait4 reap. No unbounded growth. Plus PID is captured once outside the loop — no repeated syscall allocation pressure. |
| T-110-03 | Tampering | PID reuse race: detector reaps child, kernel frees PID, unrelated process inherits PID, engine.go:335 CancelContext fires Process.Kill on the wrong PID | mitigate | Detector calls sess.CancelContext() BEFORE closing PTY and BEFORE returning (Q1 locked decision). Cancel triggers cmd.Cancel = Process.Kill while we still own the PID. The subsequent engine.go:335 CancelContext becomes idempotent. |
| T-110-04 | Repudiation | Exit code 0 reported for a session that was actually signaled | accept | We follow POSIX 128+signal convention (RESEARCH §3); signaled exits get exitCode 137 (SIGKILL), 143 (SIGTERM), etc. — distinguishable from clean exit 0. SHELL-12 frontend gate ignores this distinction (auto-closes on any natural exit per project memory). |
| T-110-05 | Information Disclosure | Exit code leaks via onExit callback to upstream consumers | accept | onExit is intra-daemon callback only; upstream (Wails app, web bridge) already had read access to exit codes via ListSessions. No new disclosure surface. |
| T-110-06 | Denial of Service | Pathological poll rate (100ms ticker per session) saturates CPU under many concurrent sessions | accept | Wait4 with WNOHANG is one of the cheapest syscalls (kernel checks ZOMBIE flag, returns immediately). At 10 Hz across realistic session counts (<50 active) the daemon overhead is well under 0.1% CPU. |
| T-110-07 | Elevation of Privilege | Detector close of PTY master triggers privilege escalation on Hub.Run | accept | No privilege boundary crossed — same process, same UID. PTY close on the kill path (cleanup.go:39-41) has been in production since v3.3 with no incident. |
| T-110-08 | Spoofing | A subprocess could fork-exec and orphan a child with the same PID we Wait4 on | accept | go-pty sets Setsid; the child is process group leader. Wait4 on the leader PID only reaps the leader, not any grandchildren. Out-of-tree forks are out of scope for SHELL-12 auto-close. |
