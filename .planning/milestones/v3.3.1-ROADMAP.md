### Phase 109: Windows daemon named-pipe IPC

**Goal:** AgentHub daemon, GUI, CLI, and TUI all work end-to-end on Windows 11 by listening on `\\.\pipe\agenthub-daemon` instead of failing to bind a Unix socket.

**Depends on:** Nothing on the v3.3.1 critical path (this is the highest-priority unblocker — Windows is currently 100% broken). Builds on the v3.3 daemon HTTP/JSON API surface (Phase 19) and on third-party PR #53 as the starting patch.

**Scope:** Adapt the daemon's `internal/daemon` listener and `DaemonClient` dialer to use `winio` named pipes on Windows and Unix sockets on macOS/Linux. PR #53 provides the structural change (new `ipc_windows.go` + `ipc_nonwindows.go` files + threading through `api.go`, `client.go`, `tray_windows.go`); v3.3 added five commits to `api.go` and `client.go` since the PR base (shell discovery routes, shell-path routes, `ShellWebShareWarned`) which are the likely conflict zones. The two new IPC files drop in clean; the conflict surface is bounded to two existing files. Surfaces involved: GUI (Wails) launching the daemon, CLI subcommands dialing the daemon, TUI dialing the daemon, tray_windows.go for tray-icon-driven daemon control. All three surfaces (GUI/TUI/CLI) must be exercised on Windows 11 per the v3.3 cross-surface parity contract.

**Requirements:** IPC-01, IPC-02, IPC-03, IPC-04, IPC-05, IPC-06

**Success Criteria** (what must be TRUE):
1. On Windows 11, launching `agenthub.exe` opens the GUI, the daemon auto-starts, and a new shell session can be created, listed, and attached — without "bind: A socket operation encountered a dead network" errors.
2. On Windows 11, `agenthub.exe list`, `agenthub.exe new <agent> <path>`, `agenthub.exe daemon status`, and `agenthub.exe tui` all connect to the running daemon over the named pipe without `EnsureDaemon` timeout.
3. On macOS and Linux, daemon and clients continue to use Unix sockets with zero behavioral change — `API.Stop()` still removes the socket file; named-pipe paths are not subject to filesystem-removal attempts.
4. A Windows regression test exercises `API.Start` + `DaemonClient.Health()` + `API.Stop` over an actual named pipe end-to-end (not just `CleanupStaleSocket` probing).
5. The merged commits in the v3.3.1 release branch credit `im-alexandre` via `Co-Authored-By` trailer (or, if re-applied from scratch, via dedicated commit-message attribution to PR #53).

**PR #53 evaluation task (mandatory, separate from coding work):**
- Fetch PR #53 locally, identify exact conflict files against `main` (`internal/daemon/api.go` + `internal/daemon/client.go` are the predicted hotspots).
- Decide rebase-then-merge vs. re-apply-from-scratch, with written rationale (e.g. "rebase succeeds with manageable conflicts in 2 files" vs. "auth surface drifted too far; re-apply preserves intent more cleanly").
- Preserve author attribution either way: `Co-Authored-By: im-alexandre <email>` on the merge commit / cherry-picked commits, OR dedicated commit message line `Re-applies PR #53 by @im-alexandre` if re-applied.

**Cross-surface verification:** Windows 11 GUI + Windows 11 CLI + Windows 11 TUI all PASS. macOS and Linux smoke tests confirm no regression.

**UAT path:** Reproduction steps on Issue #52 — fresh Windows 11 install, `agenthub.exe daemon run`, observe failure on `main`; after fix, same command succeeds and creates a session. Full GUI/CLI/TUI smoke per the v3.3 Phase 108 contract.

### Phase 110: Linux PTY natural-exit detection

**Goal:** On Linux, a shell session whose child process exits cleanly causes the GUI tab / TUI list entry to auto-close — matching macOS behavior shipped in v3.3 SHELL-12.

**Depends on:** v3.3 Phase 107 (SHELL-12 `autoCloseRef`-gated tab auto-close on `session:exit` with exit-code-0 normalization). This phase fixes the daemon-side blocker that prevents that frontend logic from firing on Linux.

**Scope:** Linux PTY EOF semantics differ from macOS — `pty.Read()` blocks indefinitely after a clean child exit on Linux amd64 with go-pty v0.2.2/v0.2.3, so the read loop never terminates and `session:exit` is never emitted. Fix is a separate exit-detector goroutine that polls `syscall.Wait4(pid, &status, WNOHANG)` (or equivalent) and explicitly closes the PTY to unblock the read loop, coordinated carefully with go-pty's internal `waitOnContext` to avoid a double-`Wait` race. Daemon-side fix in `internal/pty` / `internal/daemon/engine.go` natural-exit path. Affects: GUI Linux (tab auto-close), TUI Linux (list entry removal). CLI attach-detach is independent of this fix, but the daemon-side session cleanup it depends on is the same path. Re-enable `TestListSessions_OnExitCallback_ReceivesNormalized` (currently `t.Skip()`'d on Linux) to lock the fix in CI.

**Requirements:** PTY-01, PTY-02, PTY-03, PTY-04

**Success Criteria** (what must be TRUE):
1. On a Linux desktop build, typing `exit` at a shell-session prompt causes the GUI tab to auto-close within ~1 second — same as macOS.
2. On a Linux TUI build, typing `exit` at an attached shell session causes the TUI list entry to disappear (or transition to terminal removal) within ~1 second.
3. `TestListSessions_OnExitCallback_ReceivesNormalized` runs (no `t.Skip()` on Linux) and passes deterministically in `linux/amd64` CI under `-race -shuffle=on`.
4. macOS and Windows shell-session natural-exit behavior is unchanged — no regression in `autoCloseRef` gating or exit-code-0 normalization.

**Cross-surface verification:** Linux GUI (typing `exit`) + Linux TUI (typing `exit` from attached state) + Linux CLI (attach-detach round-trip not regressed) all PASS. macOS GUI/TUI/CLI regression smoke: typing `exit` still auto-closes.

**UAT path:** Issue #57 reproduction — Linux desktop build, open a shell session, type `exit 0`, observe tab/list-entry auto-close. Repeat with non-zero exit (`bash -c 'exit 7'`) to confirm v3.3 final SHELL-12 behavior holds ("auto-close on any natural exit" per project memory `project_shell_exit_toast_descoped`).

### Phase 111: Web bridge OSC/DA response consumption

**Goal:** On the web-served terminal, OSC color-query (10/11) and Device Attributes (CSI c) responses are consumed by the web bridge and do not leak into shell stdin — so `chafa --format=sixel <png>` produces a clean prompt on the web surface, matching desktop.

**Depends on:** v3.2 Phase 96 (image addon, sixel rendering on web) — the bug surfaces specifically when chafa probes the terminal before rendering. Phase 93 (web vendoring + parity) — web bridge is the affected component.

**Scope:** Web-only bug (desktop unaffected — Wails webview goes through xterm.js directly and consumes those responses cleanly; the dedicated web relay path in `internal/webserver` does not). Fix lives in the web bridge / relay code (`internal/webserver/relay.go` or equivalent) that proxies WebSocket frames between browser and PTY. The bridge currently does not strip / consume OSC 10/11 / DA1 responses that xterm.js (on the browser) emits in reply to terminal queries from the running program — so chafa's color queries get echoed back to the shell stdin instead of being absorbed. Pre-existing (not a v3.3 regression). Cross-surface parity (chafa sixel on web vs. desktop) is the release gate.

**Requirements:** WEB-01, WEB-02, WEB-03

**Success Criteria** (what must be TRUE):
1. In a web-shared shell session, `chafa --format=sixel /tmp/<png>` renders the image and returns to a clean prompt with no leaked `10;rgb:…`, `11;rgb:…`, or `62;4;9;22c` text on stdin.
2. Web ↔ desktop chafa sixel parity holds: the same command on a Wails-attached session and a browser-attached session of the same daemon produces equivalent clean output (sixel rendering on both, no spurious chars).
3. A Go-level (or e2e) regression test exercises the OSC response consumption path on the web bridge; a future regression in the response-handling code fails in CI.

**Cross-surface verification:** Web (Chrome + Safari) + Desktop GUI both PASS chafa sixel test. CLI/TUI unaffected (no web bridge involved).

**UAT path:** Issue #54 reproduction steps — create a shell session, enable web sharing, open the web URL, run `chafa --format=sixel /path/to/test.png`, observe clean prompt (currently shows `10;rgb:c4c4d4d4d4d4` etc. leaked into the next prompt line).

### Phase 112: WebGL recovery banner rendering

**Goal:** When the terminal's WebGL context is lost, a `WebGLRecoveryBanner` renders inside `.banner-stack` and auto-dismisses after 8s, restoring the Phase 93 user-visible recovery flow.

**Depends on:** v3.2 Phase 93 (WebGL recovery banner contract — the banner exists, but doesn't render in the live code path; DOM fallback continues to work, which is why the bug shipped undetected).

**Scope:** Pure frontend bug. Root cause suspected in `frontend/src/components/TerminalPanel.tsx:391-395` — likely `onContextLoss` closure rot (banner-state setter captured at mount time, no longer wired to the current React tree by the time loss occurs). Fix is local to `TerminalPanel.tsx` and adjacent banner state; no daemon-side changes. Frontend-only surface (GUI desktop + web both share this React component, so both benefit from one fix).

**Requirements:** UI-01, UI-02

**Success Criteria** (what must be TRUE):
1. After triggering `WEBGL_lose_context.loseContext()` from DevTools console, `document.querySelector('.webgl-recovery-banner')` is non-null and the banner is visible in `.banner-stack`.
2. The banner auto-dismisses after 8 seconds (Phase 93 contract).
3. DOM fallback continues to work after WebGL loss — terminal content remains readable; the banner-rendering fix does not regress the fallback path.
4. The fix renders the banner on both desktop (Wails webview) and web (browser) surfaces — single React component shared between both.

**Cross-surface verification:** Desktop GUI (DevTools console — `wails dev` or web-share to Chrome per project memory `project_wails_devtools_disabled_in_prod`) + Web (Chrome DevTools console) both PASS context-loss + banner-render test.

**UAT path:** Issue #55 reproduction — open a terminal session, open DevTools, run `document.querySelector('canvas').getContext('webgl2').getExtension('WEBGL_lose_context').loseContext()`, observe banner appears in `.banner-stack`, terminal continues working via DOM fallback.

### Phase 113: iPad terminal touch-scroll

**Goal:** On iPad Safari and iPad Chrome, single-finger drag on the terminal area scrolls xterm scrollback — matching desktop wheel-scroll behavior.

**Depends on:** v3.2 Phase 96/Phase 95 (web-links + image surface on iPad — touch-event semantics on the terminal container are the same shared surface).

**Scope:** Pure frontend bug. Fix is `touchstart`/`touchmove` event wiring on the terminal container (or `touch-action: pan-y` CSS opt-in to delegate scroll to the browser's native touch-scroll). The xterm-helper-textarea currently captures touch events and prevents scrollback navigation. Frontend-only surface (web only — Wails desktop has no touchscreen path). Substantially independent from Phase 112 — different root cause (touch event capture, not closure rot), different verification surface (physical iPad, not desktop DevTools). Bundling with Phase 112 would muddy verification.

**Requirements:** UI-03, UI-04

**Success Criteria** (what must be TRUE):
1. On iPad Safari, single-finger drag (up/down) on the terminal area scrolls xterm scrollback exactly as desktop mouse-wheel does.
2. On iPad Chrome, same behavior.
3. Two-finger drag on the terminal area does not pan the page viewport (touch-scroll is consumed by xterm, not the browser, when started on the terminal).
4. Desktop browser mouse-wheel scrolling is not regressed by the touch handlers.
5. Existing iPad tap-on-link cluster (Issue #56 sibling Issue #46 / UAT-04 carry-over) is not regressed — taps on OSC 8 hyperlinks still fire the click handler.

**Cross-surface verification:** iPad Safari + iPad Chrome (physical iPad required — same hardware used for v3.3 UAT-04). Desktop Chrome regression smoke for mouse-wheel scroll.

**UAT path:** Issue #56 reproduction — open a web-shared shell session on iPad, scroll back through a long terminal history with single-finger drag, confirm scrollback moves. Tap an OSC 8 hyperlink to confirm tap-on-link still works.

### Phase 114: CI test stability — webserver capability test flake

**Goal:** `TestPluginConfigStream_ExpiredCap_Returns401` passes deterministically (100/100 runs) on Linux CI under `-race -shuffle=on`, returning 401 (not 403), with the root cause identified and fixed (not papered over).

**Depends on:** Nothing on the critical path — this is independent CI hygiene. Builds on v3.2 Phase 92's `internal/webserver` capability/SSE plumbing.

**Scope:** Flaky test in `internal/webserver/plugin_config_stream_test.go` returns 403 instead of 401 on roughly 1 in N Linux CI runs under `-race -shuffle=on`. Root cause is most likely test-state pollution across `internal/webserver` tests (testServer / EnableSession / SetSigningKey leaking between tests under specific shuffle orderings), but base64 strict-decode variance and HMAC implementation are alternative hypotheses listed on Issue #58. **Investigation-first** phase: identify the actual root cause in writing before applying any fix. No rerun-pass hacks; the fix must address why the test sometimes returns 403, not how to suppress the flake. Linux CI surface only (test passes deterministically on macOS in author's experience; investigation should confirm).

**Requirements:** TEST-01, TEST-02

**Success Criteria** (what must be TRUE):
1. `TestPluginConfigStream_ExpiredCap_Returns401` returns 401 in 100/100 consecutive runs on Linux under `go test -race -shuffle=on -count=100 ./internal/webserver/`.
2. The fix commit (or accompanying note) states the root cause in writing — e.g. "EnableSession state leaks across tests when test X runs before test Y under shuffle ordering Z; reset moved to `t.Cleanup`."
3. The fix does NOT mask the underlying issue (no `t.Skip`, no retry loop, no `-shuffle=off` workaround) — it removes the source of nondeterminism.
4. macOS CI continues to pass; no other test in `internal/webserver` regresses.

**Cross-surface verification:** N/A (CI-only fix, no user surface). Validation: Linux CI green across 100 consecutive runs at the merge commit.

**UAT path:** Issue #58 — reproduce via `go test -race -shuffle=on -count=200 ./internal/webserver/` on Linux, observe at least one 403 result; after fix, 200/200 pass with 401.
