# Phase 49: App Menus & Version Injection - Research

**Researched:** 2026-04-06
**Domain:** Wails v2 application menus (macOS), Go ldflags version injection, React build-time constants, CSS border-radius
**Confidence:** HIGH

## Summary

Phase 49 addresses five self-contained requirements in the Wails v2 desktop app: macOS menu bar integration (MENU-01, MENU-02), build-time version injection from Go to the React frontend (VER-01, VER-02), and a minor CSS UI tweak to the Welcome tab logo (UI-01).

The Wails v2 menu API is fully documented in the installed module at `~/go/pkg/mod/github.com/wailsapp/wails/v2@v2.10.2/pkg/menu/`. It provides `AppMenu()`, `EditMenu()`, and `WindowMenu()` role-based helpers that delegate to native macOS menu behavior. Adding them to the `options.App.Menu` field in `main.go` is the entire backend change for MENU-01 and MENU-02. The critical ordering pitfall is already documented in `STATE.md`: `NewMenu()` → `AppMenu()` → `EditMenu()` → any custom submenus. No new dependencies are required.

For version injection, the standard Go pattern is a package-level `var Version = "dev"` in `main.go` that gets overridden by `-ldflags "-X main.Version=v1.9.0"` at build time. The frontend receives this value through a bound Wails method `GetVersion() string` on the `App` struct. `WelcomeTab.tsx` currently hardcodes `VERSION = '1.0.0'`; it must be refactored to call the Wails binding instead. The existing test (`WelcomeTab.test.tsx`) checks for the hardcoded string and will need updating.

**Primary recommendation:** All changes are mechanical and self-contained. One new Go file (`menu.go`) for the menu constructor, modifications to `main.go` (Version var + Menu option), one new bound method on `App`, updates to `WelcomeTab.tsx`, `style.css`, `build.sh`, and the CI release workflow. No new external libraries needed.

### Pattern 1: Wails Menu Construction (MENU-01, MENU-02)

**What:** Build a `*menu.Menu` and assign it to `options.App.Menu` in `runGUI()`.
**When to use:** Once, at app startup — menus are static.

**Critical ordering rule (from STATE.md):** `NewMenu()` → `AppMenu()` → `EditMenu()` → custom submenus. Deviating from this order causes macOS menu rendering failures.

```go
// Source: ~/go/pkg/mod/github.com/wailsapp/wails/v2@v2.10.2/pkg/menu/menuroles.go
// and STATE.md accumulated context

import (
    "github.com/wailsapp/wails/v2/pkg/menu"
    "github.com/wailsapp/wails/v2/pkg/menu/keys"
)

func appMenu() *menu.Menu {
    m := menu.NewMenu()
    m.Append(menu.AppMenu())   // macOS: AgentHub > About, Services, Hide, Quit
    m.Append(menu.EditMenu())  // macOS: Edit > Undo, Cut, Copy, Paste, Select All
    // File submenu (custom)
    fileMenu := m.AddSubmenu("File")
    fileMenu.AddText("New Session", keys.CmdOrCtrl("n"), nil)
    fileMenu.AddSeparator()
    fileMenu.AddText("Close Tab", keys.CmdOrCtrl("w"), nil)
    // Window submenu
    m.Append(menu.WindowMenu()) // macOS: Window > Minimize, Zoom, etc.
    // Help submenu (custom)
    helpMenu := m.AddSubmenu("Help")
    helpMenu.AddText("AgentHub Help", nil, nil)
    return m
}
```

Then in `runGUI()`:

```go
err := wails.Run(&options.App{
    // ... existing fields ...
    Menu: appMenu(),
})
```

**Note on File menu:** Wails v2.10.2 has `FileMenuRole` commented out in `menuroles.go` — the role exists as a constant but the helper function is commented out. Use a custom submenu for File instead of `menu.FileMenu()`.

**Note on Help menu:** Similarly, `HelpSubMenuRole` and the `HelpSubMenu()` helper are commented out. Use a custom `AddSubmenu("Help")` call.

### Pattern 2: Go ldflags Version Injection (VER-01)

**What:** Package-level `var` with a sentinel default value, overridden at build time.
**When to use:** Any `wails build` or `go build` invocation for release builds.

```go
// In main.go — package-level (before func main)
// Version is injected at build time via:
//   wails build -ldflags "-X main.Version=v1.9.0"
// Falls back to "dev" in local dev builds.
var Version = "dev"
```

Wails `wails build` passes flags through to the underlying `go build`. The `-ldflags` flag to `wails build` maps directly.

Local dev: `var Version = "dev"` (no flags needed)
Production: `wails build -ldflags "-X main.Version=v1.9.0" -tags wailsassets`

### Pattern 3: Version Propagation to Frontend (VER-02)

**What:** A Wails-bound method on `App` that returns the package-level `Version` variable.
**When to use:** Called once on mount in `WelcomeTab.tsx`.

```go
// In app.go — add to existing bound methods
// GetVersion returns the application version injected at build time.
// Returns "dev" in local development builds.
func (a *App) GetVersion() string {
    return Version
}
```

`WelcomeTab.tsx` must be refactored from:

```typescript
const VERSION = '1.0.0'
// ...
<p className="welcome-tab__version">v{VERSION}</p>
```

To a `useEffect`/`useState` pattern:

```typescript
import { GetVersion } from '../wailsjs/go/main/App'

export function WelcomeTab(): React.ReactElement {
  const [version, setVersion] = useState('...')
  useEffect(() => {
    GetVersion().then(setVersion).catch(() => setVersion('dev'))
  }, [])
  // ...
  <p className="welcome-tab__version">{version}</p>
}
```

**Note:** The `GetVersion` call is async (all Wails bindings return Promises). A loading state of `'...'` or `'dev'` prevents empty display during the brief async gap.

**Note on wailsjs regeneration:** After adding `GetVersion()` to `app.go`, run `wails dev` (or `wails generate module`) to regenerate `frontend/src/wailsjs/go/main/App.js` and `App.d.ts`. Without regeneration, the TypeScript import won't resolve.

### Pattern 5: build.sh and CI ldflags Updates (VER-01)

**build.sh** — `build_macos()` becomes:

```bash
build_macos() {
  local VERSION="${BUILD_VERSION:-dev}"
  "$WAILS" build -platform darwin/universal -clean \
    -ldflags "-X main.Version=${VERSION}" \
    -tags wailsassets
}
```

Caller: `BUILD_VERSION=v1.9.0 ./build.sh --platform macos`

**release.yml** — the `dAppServer/wails-build-action` passes `go-build-args`:

```yaml
- name: Build macOS app with Wails
  uses: dAppServer/wails-build-action@main
  with:
    build-name: agenthub
    build-platform: darwin/universal
    go-build-args: -ldflags "-X main.Version=${{ github.ref_name }}"
```

(Same pattern for Windows and Linux build steps.)

### Anti-Patterns to Avoid

- **Wrong menu order:** Appending `EditMenu()` before `AppMenu()` — macOS requires AppMenu first or keyboard shortcuts fail silently. STATE.md documents this as a known Wails pitfall.
- **Using FileMenu() or HelpSubMenu() roles:** These helpers are commented out in Wails v2.10.2 source. Calling them will not compile. Use `AddSubmenu("File")` and `AddSubmenu("Help")` instead.
- **Hardcoding version in WelcomeTab.tsx:** Defeats the whole VER-01/VER-02 purpose. Remove the `const VERSION` entirely.
- **Forgetting to regenerate wailsjs:** Adding `GetVersion()` to `app.go` without running `wails dev` leaves the TypeScript binding stale — import will fail.
- **Injecting version via Vite `define` only:** Fragile — doesn't flow through the Go layer, and requires a second injection mechanism separate from ldflags.
- **Not adding `-tags wailsassets` alongside ldflags:** Production builds need both flags (project memory note from phase 26).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Clipboard shortcuts in terminal | Custom JS keyboard handler | `menu.EditMenu()` via `EditMenuRole` | macOS native NSMenu handles clipboard routing to focused responder; custom JS handlers fight the OS |
| Keyboard shortcuts for menus | Manual keydown listeners | `keys.CmdOrCtrl("n")` accelerators | Wails passes these to the native menu bar |
| Version at runtime | Network call / file read | Go ldflags `-X` | Compile-time injection is reliable, zero overhead, no runtime failure mode |

**Key insight:** macOS clipboard operations in WKWebView require the native menu bar's Edit menu to route events correctly. Without it, `document.execCommand('paste')` and xterm.js clipboard operations fail silently on macOS — the OS requires a menu item with the paste selector to be present.

## Common Pitfalls

### Pitfall 1: Menu Order on macOS
**What goes wrong:** Menu bar shows items in wrong order or keyboard shortcuts don't fire.
**Why it happens:** macOS expects AppMenu as index 0. Wails respects insertion order.
**How to avoid:** Always: `NewMenu()` → `Append(AppMenu())` → `Append(EditMenu())` → custom submenus.
**Warning signs:** Cmd+C/Cmd+V still broken after adding EditMenu; verify order in code.

### Pitfall 2: Commented-Out Role Helpers
**What goes wrong:** Compiler error `menu.FileMenu undefined` or `menu.HelpSubMenu undefined`.
**Why it happens:** These functions are commented out in Wails v2.10.2 `menuroles.go` (lines 124-214 are inside `/* ... */`). Only `EditMenu()`, `WindowMenu()`, and `AppMenu()` are active.
**How to avoid:** Use `m.AddSubmenu("File")` and `m.AddSubmenu("Help")` for custom menus.
**Warning signs:** Compile error referencing `menu.FileMenu` or `menu.HelpSubMenu`.

### Pitfall 3: Wailsjs Not Regenerated After Adding Bound Method
**What goes wrong:** TypeScript import `import { GetVersion } from '../wailsjs/go/main/App'` causes "not exported" or type error.
**Why it happens:** `frontend/src/wailsjs/go/main/App.js` and `App.d.ts` are auto-generated — not manually edited.
**How to avoid:** Run `wails dev` or `wails generate module` after adding `GetVersion()` to `app.go`.
**Warning signs:** TypeScript compilation error in `WelcomeTab.tsx`; or `GetVersion is not a function` at runtime.

### Pitfall 4: WelcomeTab Test Checks Hardcoded Version String
**What goes wrong:** `pnpm run test` fails after removing `const VERSION = '1.0.0'`.
**Why it happens:** `WelcomeTab.test.tsx` line 18 asserts `expect(raw).toContain("VERSION = '1.0.0'")`.
**How to avoid:** Update the test to check for the `GetVersion` import and `useState` usage instead.
**Warning signs:** Test failure on `"VERSION = '1.0.0'"` assertion.

### Pitfall 5: ldflags Not Applied in build.sh Linux Docker Path
**What goes wrong:** Linux build produces binary with `Version = "dev"`.
**Why it happens:** `build_linux()` in `build.sh` uses a raw `go build` inside Docker, not `wails build` — the ldflags are not passed through.
**How to avoid:** Add `-ldflags "-X main.Version=${VERSION}"` to the `go build` call inside the Docker bash heredoc.
**Warning signs:** Binary reports `dev` version on Linux; macOS/Windows show correct version.

## Open Questions

1. **File menu action callbacks**
   - What we know: `fileMenu.AddText("New Session", keys.CmdOrCtrl("n"), nil)` — the `nil` callback means the shortcut fires no Go handler.
   - What's unclear: Whether Cmd+N and Cmd+W need actual callbacks to open/close tabs, or if they can remain non-functional for v1.9 (requirement only says "conventional keyboard shortcuts appear").
   - Recommendation: Leave callbacks nil for now; MENU-01 says "appears in menu bar with conventional keyboard shortcuts" — it does not say the shortcuts must trigger tab creation. Functional shortcuts can be a follow-on task.

2. **Help menu content**
   - What we know: The requirement says "Help menu appears."
   - What's unclear: Whether "AgentHub on GitHub" link item needs a callback to open a browser URL.
   - Recommendation: Add one item with a `runtime.BrowserOpenURL` callback pointing to the GitHub repo URL.
