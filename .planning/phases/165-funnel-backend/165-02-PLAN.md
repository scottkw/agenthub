<objective>
Add the daemon/API half of the Tailscale Funnel lifecycle on top of 165-01's webserver primitives. Introduce the per-session `funnelSessions` reference-count map and the `funnelExpiry` timer map on the API struct, the `POST /sessions/{id}/funnel` endpoint (`handleSetSessionFunnel`), the single `disableFunnelForSession` teardown helper wired through every teardown trigger, the Funnel-aware share-URL builders, daemon-restart lingering-Funnel clearing, and the `SessionInfo.funnelActive` poll field.

Purpose: 165-01 made `ws.EnableFunnel` / `ws.DisableFunnel` / `ws.FunnelBaseURL` / `ws.ClearLingeringFunnel` exist but inert (no session can be Funnel-enabled, the dual-origin branch is fail-closed). This plan makes Funnel reachable per-session and guarantees it is torn down on every exit path. The Wails on-ramp (App.SetSessionFunnel + DaemonClient.SetSessionFunnel + the app.go SessionInfo mirror) lands in 165-03.

Locked planning decisions honored here (from 165-RESEARCH.md Open Questions):
- Port is always 443 (handleSetSessionFunnel calls `ws.EnableFunnel(ctx, 443)`); the `CheckFunnelAccess` error is surfaced verbatim to the HTTP caller as a 400 (FNL-06 path, error body is user-facing).
- Daemon-restart clears any lingering Funnel serve config (Open Question #3 → clear on startup; Funnel state is ephemeral like grants).
- `funnelActive bool` is added to `SessionInfo` for frontend polling (Open Question #1 → polling, zero new IPC). Phase 165 only sets the field server-side; no frontend wiring here.
- Reference counting: `ws.DisableFunnel` is called ONLY when `len(funnelSessions)==0` (Anti-Pattern 3 — never tear down a still-active sibling session).

Output: modified `api.go` (struct maps, route, handler, teardown helper + 3 wired sites, 2 URL builders, startup clear, SessionInfo population), modified `types.go` (request/response + SessionInfo field), modified `webserver/funnel_client.go` (exported test seam), new `daemon/funnel_test.go`, TESTING.md registration.
</objective>
