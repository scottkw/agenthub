<objective>
Add the atomic webserver-package half of the Tailscale Funnel lifecycle: promote `local.Client` to a `WebServer` struct field, introduce the injectable `funnelClient` interface seam, implement `EnableFunnel` / `DisableFunnel` / `FunnelBaseURL` / `ClearLingeringFunnel`, and extend the Origin allowlist to a dual-origin (tailnet + Funnel) check. The Funnel-enable lifecycle and the Origin fix ship together in this single plan so no releasable state exists where `EnableFunnel` works but the Origin check still 403s every external guest (Pitfall 2 / atomicity constraint).

Purpose: This is the foundation every later plan depends on. The daemon plan (165-02) calls `ws.EnableFunnel` / `ws.DisableFunnel` / `ws.FunnelBaseURL` / `ws.ClearLingeringFunnel`; the Wails bridge (165-03) closes the loop. Because no session can be Funnel-enabled until the daemon endpoint lands in 165-02, the dual-origin secondary branch added here is inert (fail-closed: `FunnelBaseURL()` returns "" until a real enable) and cannot widen access on its own.

Locked planning decisions honored here:
- Port is hard-coded 443 (Open Question #2 → always 443; surface the `CheckFunnelAccess` error verbatim if 443 is blocked; no 8443/10000 fallback logic).
- `local.Client` is stored by value (`lc local.Client`, zero-value usable) — never by pointer.
- `BaseURL()` is NOT modified — it continues to return the tailnet URL for the tray icon, QR code, and Settings copy button. `FunnelBaseURL()` is a separate method.

Output: New `funnel_client.go` (interface + production wiring), modified `server.go` (struct fields + 4 methods + Stop teardown), modified `origin_mw.go` + `capability_mw.go` (dual-origin), new `funnel_test.go` (Wave 0 scaffolding + fakeFunnelClient + behavior tests).
</objective>
