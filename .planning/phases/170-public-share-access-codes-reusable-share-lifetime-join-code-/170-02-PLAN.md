<objective>
Wire the reusable read code into the daemon Funnel lifecycle: mint it once per Funnel-enable (bound to the
read-only token), cache it per session so repeat capability re-issues don't rotate it, surface it on
`IssueCapabilitiesResponse.PublicReadCode`, and revoke it in the single teardown chokepoint so it dies exactly
when the share does — on every trigger, not only when a timer coincidentally fires.

Purpose: FNL-08 requires a code that (a) resolves read-only, (b) is idempotent, (c) is bounded to the share's
lifetime with an ≤8h entropy backstop. The frontend (Wave 3) reads `resp.publicReadCode` off the same warm-up
`IssueCapabilities` call it already makes to obtain the Funnel read URL.
Output: the daemon-side minting/caching/revocation machinery + its regression tests.

## Artifacts this plan produces
- `funnelReadCode map[string]string` (sessionID → cached reusable code) and
  `funnelReadCodeTTL map[string]time.Duration` (sessionID → chosen per-code TTL), guarded by `a.mu`
- `funnelReadCodeMaxTTL = 8 * time.Hour` const (the entropy-safety backstop)
- `PublicReadCode` field on `IssueCapabilitiesResponse` (JSON `publicReadCode`)
- Idempotent mint-and-cache block in `issueCapabilitiesForSession` (read-token-only)
- Revoke + cache-clear in `disableFunnelForSession`

## Design decision (resolves RESEARCH Open Questions 1 & 2)
- **Wire field placement:** `PublicReadCode` lives on `IssueCapabilitiesResponse` ONLY (not `SetSessionFunnelResponse`).
  The frontend's warm-up flow re-issues `IssueCapabilities` after `funnelActive` flips (SessionShareModal.tsx:377),
  which is exactly where the read URL is obtained — the code rides along on that same response. This also serves
  modal-reopen for an already-active share.
- **ExpiresIn==0 backstop:** cap the per-code TTL at `funnelReadCodeMaxTTL` (8h). Explicit Revoke is the PRIMARY
  "dies with the share" mechanism; the TTL is defense-in-depth. This preserves the "2^40 over ≤8h" safety claim.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| owner (loopback daemon socket) → mint | Trusted; the daemon chooses which token backs the code |
| minted code → capability token scope | The security-critical mapping: reusable code must resolve read-only |
| teardown triggers → live code | Any of 4 in-process paths must invalidate the code immediately |

| T-170-02 | Info Disclosure / EoP | disableFunnelForSession | high | mitigate | Explicit Revoke + cache-clear in the single teardown chokepoint; `TestFunnelTeardown_AllTriggers` asserts every trigger invalidates the code (not TTL-only) |
