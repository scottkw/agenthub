<objective>
Fix Phase 113 / Issue #56: on iPad Safari and iPad Chrome, single-finger drag on the terminal area must scroll xterm scrollback (matching desktop mouse-wheel) without regressing desktop wheel scroll or the iPad OSC 8 tap-on-link path.

Purpose: xterm.js 6.0.0 has zero touch handlers attached. The CONTEXT root-cause guess (`.xterm-helper-textarea` capturing touches) was refuted by RESEARCH — that textarea is offscreen at `left:-9999em` and intercepts nothing. The real fix is to attach our own touch handlers to the React-owned terminal container `<div>` and translate vertical drag deltas into `term.scrollLines(N)` calls.

Output:
- `frontend/src/lib/touchScrollHandler.ts` — new pure module exporting `attachTouchScroll(container, term) => cleanup`
- Vitest tests (pure-function unit tests + `?raw`/css source-grep tests)
- `TerminalPanel.tsx` useEffect wiring (mirrors existing sessionId-keyed mount-effect pattern at line ~195)
- `style.css` companion: `touch-action: pan-y` on `.terminal-session-container`
- `113-VERIFICATION.md` UAT scaffold with iPad Safari + iPad Chrome marked `human_needed` (macOS executor cannot perform iPad UAT — physical hardware required)
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| iPad browser → frontend JS | Untrusted TouchEvent geometry crosses here (clientY values from real OS input) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-113-01 | Tampering | TouchEvent `clientY` arithmetic in `touchScrollHandler.ts` | accept | Values come from a browser-trusted DOM API; used only in arithmetic (subtraction, Math.trunc, division). No DOM injection, no eval, no fetch. ASVS V5 lightweight: input is a number bounded by viewport pixel range; multiplied by < 1 (lines = dy / cellH); overflow risk nil. |
| T-113-02 | Tampering | OSC 8 link tap path (`WebLinksAddon` at TerminalPanel.tsx:489-558) | mitigate | DO NOT preventDefault on touchend regardless of drag state. Sub-threshold (< 8px) touchmove also does NOT preventDefault. This guarantees iOS fires the synthetic click and the existing `getRisk` + `LinkConfirmPopover` security pipeline runs unchanged. Verified by Task 1 Test 5 and Task 4 UAT-04. |
| T-113-03 | Denial of Service | Excessive touchmove handler frequency | accept | TouchEvent firing rate is browser-throttled (~60Hz). Handler is O(1) arithmetic + one method call. No allocation in the hot path beyond closure-captured numbers. Negligible. |
| T-113-04 | Information Disclosure | New module reads `term._core._renderService.dimensions.css.cell.height` (private API) | accept | This private path is already in production at `TerminalPanel.tsx:29` (`fitTerminal`). It exposes only render-layout numbers, no user data. Same blast radius as existing usage. |
| T-113-05 | Spoofing | Synthetic touch events from DevTools touch-emulation triggering both touch handler AND mouse-wheel | accept | Documented as a DevTools-emulation artifact in RESEARCH Pitfall 4. Physical devices route through only one path. No fix; UAT spec calls out physical hardware. |
