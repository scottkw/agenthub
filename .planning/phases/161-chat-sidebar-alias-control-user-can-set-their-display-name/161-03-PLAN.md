<objective>
Add the alias control to the shared ChatPanel header — the single user-facing deliverable of this phase. Because all three hosts (HubInteractiveModal, TerminalChatHost, WebShareSessionView) mount the same <ChatPanel>, adding the control here gives GUI tab + Hub modal + web-share guest the feature with ZERO host-component changes (parity by construction, approach c).

The control is a "chatting as: «name» ✏️" header affordance (RESEARCH-recommended over inline-roster edit, since the roster renders avatar initials only). On commit it client-validates (mirroring Go ValidateAlias exactly) and calls the live clientRef.sendAliasSet from Plan 161-02. The server (already complete) persists via AliasStore and rebroadcasts presence, which lands in the existing onPresence callback and updates the roster for everyone — no local authoritative echo needed.

Purpose: Deliver ALIAS-UI-01 (set alias from the shared sidebar, all surfaces) and the client-validation half of ALIAS-UI-02 (respects ValidateAlias). Persistence + roster/author propagation is the existing backend (Plan 161-01 only adds the self hint for pre-fill).

Output: validateAlias mirror + header control + commit handler + pre-fill wiring (desktop roster lookup + web onSelf) + CSS + extended ChatPanel unit tests.

Load-bearing constraints (do NOT regress):
- Alias control stays enabled when isReadOnly (D-06) — do not copy disabled={isReadOnly} from the Send button.
- Client validation mirrors ValidateAlias by CODE POINTS (Array.from), not UTF-16 length.
- Past messages are NOT renamed (per-message AuthorAlias snapshot) — scope verification to roster + future messages only.
- Keep ChatPanel un-forked.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user input → alias control | Untrusted free text. Client validateAlias (defense-in-depth) gates before send; server ValidateAlias is authoritative. |
| server-broadcast alias → React render | Alias appears in the roster + author header. Rendered as text by React's default escaping — never via HTML injection. |
| read-only cap → alias control | RO guests may set an alias by design (D-06); only chat-send / @session inject / PTY remain RO-gated. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-161-02 | Tampering | alias rendered in roster + chat author header | medium | mitigate | Alias passes server ValidateAlias (no control chars) and is rendered as React text (no dangerouslySetInnerHTML); chat bodies already use rehype-sanitize (SEC-03), author names are a separate text-only render path. No HTML/XSS vector. |
| T-161-04 | Tampering | client validateAlias mirror | medium | mitigate | Mirrors Go ValidateAlias by code points (Array.from), reject-not-truncate; it is defense-in-depth for UX (server is authority and sends no NAK). |
| T-161-01 | Spoofing | RO/any guest sets an alias mimicking another participant | low | accept | Aliases are user-chosen display names, NOT identity; the stable personKey/tailnetID remains the real identity in presence. Out of scope to prevent per RESEARCH Security Domain. |
| T-161-03 | Elevation of Privilege | RO guest using an un-gated alias control | low | accept | Intentional (D-06). Alias-set grants no terminal/inject capability; PTY input + @session inject stay RO-gated (untouched this phase). Accepted design, not a privilege escalation. |
| T-161-SC | Tampering | package installs | n/a | accept | No npm packages added — RESEARCH Package Legitimacy Audit: not applicable. |
