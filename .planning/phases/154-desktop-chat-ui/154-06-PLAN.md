<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Composer keyboard/pointer input → frame encoders | The user's keystrokes and gestures decide which frame (chat-send 0x31 vs session-inject 0x35) is emitted — the only client-side gate on PTY writes. |
| ChatPanel → relay WS | Both encodeChatSendFrame and encodeSessionInjectFrame cross to the server, which independently re-gates (plan 154-01 / Phase 153). |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-154-02 | Elevation of Privilege | composer Enter vs press-and-hold | high | mitigate | D-08: inject (0x35) is emitted ONLY by a completed ~600ms press-and-hold; Enter, taps, and autocomplete-Enter always route to chat-send (0x31) on a strictly separate code path (Pitfall 7). Server-side, only 0x35 writes to PTY and HandleInject re-gates on RW (plan 154-01 / Phase 153 SEC-01). Unit tests assert tap=no-op, hold=one inject, Enter≠inject. |
| T-154-01 | Tampering | echoed message render | high | mitigate | Sent/echoed bodies render through ChatMessage's rehype-sanitize pipeline (SEC-03, plan 154-03); the "-t sec-03" integration test re-proves inertness end-to-end. |
| T-154-11 | Spoofing | unread badge state | low | accept | Badge counts are local UI state derived from received frames; no security decision depends on them. |
</threat_model>
