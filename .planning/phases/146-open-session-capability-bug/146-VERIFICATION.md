### Gaps Summary

**Root cause:** `app.go` was not modified in Phase 146. This single omission severs the entire end-to-end data path.

**Gap 1 (BLOCKER — feature dead on arrival):**

The Wails-exposed Go struct `RemoteSession` in `app.go` (L57-63) has no `ROJoinCode`/`RWJoinCode` fields. `GetRemoteSessionsWithMeta` (L1209-1215) constructs `RemoteSession` literals copying only `ID/Name/CLIType/Status/URL`. Wails serializes Go structs to JSON by reflection — fields that do not exist in the struct are never present in the RPC response. The frontend's `session.roJoinCode` is always `undefined`. `handleOpenRemoteSession` (App.tsx L1085) checks `if (!session.roJoinCode)` — this branch is always taken, always surfaces the "not shared" error banner, and always returns without calling `ExchangeJoinCodeAtURL`. Open in browser is broken for every remote session, identical behavior to pre-Phase-146. The unit tests all pass because no test crosses the `app.go` boundary with join-code assertions.

**Exact fix:** Add `ROJoinCode string \`json:"roJoinCode,omitempty"\`` and `RWJoinCode string \`json:"rwJoinCode,omitempty"\`` to the `RemoteSession` struct in `app.go` (L57-63), and copy `ROJoinCode: s.ROJoinCode, RWJoinCode: s.RWJoinCode` in the `GetRemoteSessionsWithMeta` struct literal (L1209-1215). Add an integration test in `app_test.go` that verifies codes survive the `app.go` conversion boundary.

**Gap 2 (BLOCKER — security, requires team decision):**

`mintSessionJoinCodes` always mints both RO and RW join codes and `handleSessionsMeta` embeds both in the unauthenticated `/api/sessions/meta` response accessible to any tailnet peer. `/join/exchange` (`server.go L536`) performs no caller-identity check — it exchanges any valid code presented. Any peer with tailnet access to the owner's machine can `curl /api/sessions/meta`, read `rw_join_code`, POST it to `/join/exchange`, and obtain a `read,write` capability token. The RESEARCH threat-model entry claiming "RW is gated by `isPeerSelf`" does not match the implementation — `isPeerSelf` is a frontend UI hint with no server-side enforcement. Additionally, for the primary #98 use case (one user, two distinct physical Macs), `isPeerSelf` always returns `false` because the remote peer's hostname is never the same as the local node's short hostname — the RW branch is unreachable dead code in practice (REVIEW WR-01).

**Options for the team:**
- Scope `mintSessionJoinCodes` to mint RO only for broadcast, and obtain RW through the already-authenticated local Unix-socket path (`issueCapabilitiesForSession`) that the owner uses for the Share modal.
- Accept the current behavior as a deliberate trade-off (document that any tailnet peer on a shared tailnet can obtain write access to any shared session) — but this contradicts the stated D-05/D-06 design intent.
- Move the owner-identity check server-side into the exchange/mint path.

This is a security design decision that cannot be auto-fixed and requires explicit team resolution.
