<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user input (rename/mkdir name) → relPath | Name text becomes part of a sandbox-relative path |
| keypress → modal/action dispatch | Confirm/inline keys must not leak to other handlers |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-126-08 | Tampering/Elevation | rename/mkdir name → path traversal | accept (mitigated server-side) | TUI constructs the destination ONLY via `joinDir(cwd, name)` (forward-slash relative join) and sends a sandbox-RELATIVE path; server-side `validateAndClean` double-validates source+dest (Phase 123). No absolute or `../` construction client-side. (SECURITY V5) |
| T-126-09 | Tampering | accidental destructive delete | mitigate | `d` always shows a confirmation modal before any DeleteFile dispatch (cross-surface confirmation parity); single keypress never deletes. |
| T-126-10 | Repudiation/UX | stray confirm key leaking to tab-cycling | mitigate | Confirm + inline-input handlers sit ABOVE handleFilesKey (Priority 5.5) in the dispatch ladder; a priority sub-test enforces it. |
| T-126-11 | Tampering | home-dir dotfile overwrite/delete | accept (mitigated elsewhere) | Server-side denylist (Phase 127) + existing live TUI `homeDirWriteWarning` (files.go:332) renders when HomeDir && FilesWrite. No new TUI work. |
| T-126-12 | Denial of Service | synchronous FS/network in Update | mitigate | All delete/rename/mkdir I/O runs in tea.Cmd closures; Update only sets state + returns cmds. Verified by the no-sync gate (Plan 04). |
</threat_model>
