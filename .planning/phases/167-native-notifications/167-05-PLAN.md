<objective>
Close the Phase 167 M-41 regression: the native macOS notification path (`sendNotification` in `tray_objc_darwin.m`) calls `[UNUserNotificationCenter currentNotificationCenter]` with no app-bundle-identifier guard and no `@try/@catch`. Phase 167 wired this crash-prone call into the always-on 5s tray poller via `App.maybeNotifyWaiting` (gated by the `NotifyOnWaiting` toggle). Under `wails dev` the process is unbundled, so the first non-waiting to waiting transition with the toggle ON raises an uncaught `NSInternalInconsistencyException` ("bundleProxyForCurrentProcess is nil") that aborts the entire GUI process — killing the toast, the session-tab attention dot, the Hub-card glow, and tab-auto-close-on-exit all at once (all four live in that one GUI process).

Harden the native path to fail safe: detect a missing bundle identifier and turn `sendNotification` into a log-and-swallow no-op, mirroring the beeep Windows/Linux wrappers' contract. Preserve the feature exactly: on a valid bundled/signed app the notification still fires normally. Add a headless regression test on the bundle-id detection primitive (the honest, runnable guard), and register it per the repo's standing TESTING.md rule.

Purpose: A genuine code regression — an always-on poller must never call a crash-prone native API unguarded. Hardening is required regardless of build type.
Output: Guarded `sendNotification` (native + Go wrapper), a headless darwin regression test, and updated TESTING.md.
</objective>

<task type="auto">
  <name>Task 1: Harden the darwin native notification path (bundle-id guard + @try/@catch + Go log-and-swallow)</name>
  <files>tray_objc_darwin.m, notification_darwin.go</files>
  <action>
Make the macOS native notification path fail safe so an unbundled/unsigned process (wails dev) can never abort the GUI process, while a valid bundled/signed .app still fires notifications unchanged.

In tray_objc_darwin.m:
- Add a small ObjC C-linkage helper `int hasValidBundleIdentifier(void)` that returns 1 when `[[NSBundle mainBundle] bundleIdentifier] != nil`, else 0. NSBundle is already available via the existing `#import <Cocoa/Cocoa.h>`.
- In `sendNotification` (the function at ~line 160), BEFORE the `dispatch_async(dispatch_get_main_queue(), ...)` call, guard synchronously: if `hasValidBundleIdentifier()` returns 0, emit exactly one `NSLog` line noting the notification was skipped because no app-bundle identifier is present, then `return` — do NOT dispatch. This is the primary fix: it prevents the crash-prone `UNUserNotificationCenter` code from ever being reached in an unbundled process.
- Defense in depth: inside the dispatch_async block, wrap the `UNUserNotificationCenter` usage (the `currentNotificationCenter` / `requestAuthorizationWithOptions` / `addNotificationRequest` sequence) in `@try { ... } @catch (NSException *e) { NSLog(...); }` so any residual bundle/entitlement fault on a signed build is swallowed and logged rather than aborting the process. Do the same for the nested `dispatch_async` block that builds and adds the request.
- Do NOT change behavior on the valid-bundle path: when `hasValidBundleIdentifier()` is 1, the existing authorization + request-add flow runs exactly as before (feature preserved — NTF-01/02/03).

In notification_darwin.go:
- Add `int hasValidBundleIdentifier(void);` to the cgo header comment block (alongside the existing `void sendNotification(...)` declaration).
- Add a package-level Go function `hasAppBundleID() bool` that returns `C.hasValidBundleIdentifier() != 0`.
- In the Go `sendNotification` wrapper, at the top, if `!hasAppBundleID()`, `log.Printf` a single line noting the notification was skipped (no valid app-bundle identifier) and `return` before any `C.CString` allocation or the `C.sendNotification` call — mirroring the beeep Windows/Linux log-and-swallow contract in notification_linux.go / notification_windows.go. Import the standard library `log` package (currently only `unsafe` is imported).
- This Go-level early-return is what the headless test in Task 2 exercises: a go-test binary is itself unbundled, so `hasAppBundleID()` returns false there, exactly reproducing the wails-dev condition.

Rationale reference: root cause and prescribed direction in .planning/debug/waiting-signals-regression.md (Resolution block) and 167-UAT.md Gaps.missing. Gap reason: an always-on tray-poller path (maybeNotifyWaiting) reached an unguarded crash-prone native API.
