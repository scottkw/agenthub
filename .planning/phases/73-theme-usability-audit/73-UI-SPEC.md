## Theme Picker Contract

This is the primary UI surface changed in Phase 73.

### Current State

- Element: `<select class="settings-panel__path-input settings-panel__theme-select">` inside `SettingsTab.tsx`
- Data source: `const THEME_NAMES = Object.keys(xtermThemes).sort()` — all 157 themes from `xterm-theme@1.1.0`
- Options render as: `{name.replace(/_/g, ' ')}` for display, raw key for value
- Max-width: 260px. Width: auto.
- Default theme: `Tomorrow_Night` (stored in `localStorage` under key `agenthub:terminalTheme`)

### Required State After Phase 73

- `THEME_NAMES` must be replaced by a curated allowlist of themes that pass the readability audit
- The allowlist is a hardcoded constant in `SettingsTab.tsx` (or a co-located file imported by it)
- All 157 themes remain in the `xterm-theme` package — only the picker list shrinks
- The `<select>` element itself, its CSS class, and its layout do not change
- The `onChange` handler and `selectedTheme` prop wiring do not change
- If the previously-stored `localStorage` theme is not in the allowlist, the app falls back to `Tomorrow_Night` silently

### Allowlist Construction Rules

The allowlist must satisfy all four success criteria from REQUIREMENTS.md THM-04:

1. Every listed theme renders readable foreground text in Claude Code, Codex, Gemini CLI, and OpenCode
2. No listed theme produces unreadable text, invisible cursors, or indistinguishable ANSI colors in any of the 4 agents
3. At least one light-background theme survives (user has a light option)
4. At least one dark-background theme survives (user has a dark option)

The audit methodology (manual or scripted) is an implementation decision for the planner — it is not specified here. The UI contract is: the picker renders the surviving list only.

### Fallback Behavior Contract

| Scenario | Behavior |
|----------|----------|
| Stored theme still in allowlist | Load normally — no visible change |
| Stored theme removed by audit | Silently fall back to `Tomorrow_Night` at startup |
| `Tomorrow_Night` itself removed by audit | Fall back to first entry in the sorted allowlist |
| Allowlist is empty (should never happen — audit guarantees at least 1 light + 1 dark) | Use `Tomorrow_Night` as hardcoded last resort |

Fallback must be silent — no toast, no modal, no error message. The user simply sees a valid theme applied.

### Option Display Format

Option labels remain: `{themeName.replace(/_/g, ' ')}` — same as today.

No grouping of light vs. dark themes in the `<select>`. Options remain sorted alphabetically.

## Interaction Contract

No new interactions are introduced. The theme `<select>` behavior is unchanged:

| Interaction | Behavior |
|-------------|----------|
| User opens picker | Dropdown shows alphabetically sorted surviving themes only |
| User selects a theme | `onThemeChange(name)` fires; theme stored to `localStorage`; terminal sessions created after this point use the new theme |
| User selects a theme that was previously valid but now removed | Not possible — removed themes are not in the list |
| App starts with a stale stored theme | Silent fallback to `Tomorrow_Night` (see Fallback Behavior Contract above) |

No new keyboard shortcuts, focus traps, or ARIA attributes required. The native `<select>` element provides all accessibility semantics.
