Create three files for release-please automation (per REL-01):

**1. `.github/workflows/release-please.yml`** — Create with exact contents:
```yaml
name: release-please

on:
  push:
    branches:
      - main

permissions:
  contents: write
  pull-requests: write

jobs:
  release-please:
    runs-on: ubuntu-latest
    steps:
      - uses: googleapis/release-please-action@v4
        id: release
        with:
          token: ${{ secrets.RELEASE_PLEASE_TOKEN }}
          config-file: release-please-config.json
          manifest-file: .release-please-manifest.json
```

**2. `release-please-config.json`** — Create at repo root with exact contents:
```json
{
  "$schema": "https://raw.githubusercontent.com/googleapis/release-please/main/schemas/config.json",
  "release-type": "simple",
  "packages": {
    ".": {
      "extra-files": [
        {
          "type": "json",
          "path": "wails.json",
          "jsonpath": "$.info.productVersion"
        }
      ]
    }
  },
  "bootstrap-sha": "7b186ce29ea24014fe4b635cb57d2563e4d67f67"
}
```

The `bootstrap-sha` value is the commit SHA of the v1.7 tag (`git rev-list -n 1 v1.7`). This prevents release-please from scanning the entire commit history and generating a massive CHANGELOG.

**3. `.release-please-manifest.json`** — Create at repo root with exact contents:
```json
{
  ".": "1.7.0"
}
```

This seeds release-please with the current version so the next Release PR targets v1.8.0. The `"."` key maps to the root package. Version is bare semver (no `v` prefix) — the action prepends `v` when creating tags.

Key decisions:
- Using `release-type: simple` (not `go`) per research — sidesteps Go type version-file bug (issue #2541)
- Using `extra-files` with JSON-path to update `wails.json` `info.productVersion` field (per user locked decision: do NOT rely on version-file config)
- Using PAT token `RELEASE_PLEASE_TOKEN` (not GITHUB_TOKEN) so Release PRs trigger downstream CI checks on build.yml
