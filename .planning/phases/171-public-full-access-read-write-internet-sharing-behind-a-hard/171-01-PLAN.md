<objective>
Build the two enforcement primitives that make public write reachable ONLY through the consent gate, plus the single-use-with-custom-TTL write-code primitive — all as siblings to existing, verified code (Phase 170 join-code lifecycle + the grant registry).

Purpose: This plan closes the internet-RCE surface at the layer that actually reaches the PTY-write path. Per RESEARCH Pitfall 1 (grep-verified), `originAllowedForWrite` is wired into exactly one call site (`requireFilesWrite`) and does NOT reach `handleWSSRelay`; the terminal-write gate is `sub.ReadOnly`, derived at WS-upgrade from grant validity + `HasPerm(claims.Perms,"write")`. Therefore grant-registration gating (D-01) is the primary and sufficient terminal-write enforcement; the origin check (D-02) is defense-in-depth for the `files.write` routes only.

Output: `IssueSingleUseWithTTL`, `RemoveGrant`, `SetRWGate`/`isRWGated` + `rwGated` map, gate-aware `originAllowedForWrite`, and the critical WS-relay integration test proving a non-gated write cap is rejected at upgrade.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet → Funnel origin → WS relay (`/sessions/{id}/ws`) | Untrusted guest presents a `?cap=` token; a valid write cap here = internet-reachable PTY command execution (RCE) |
| public internet → `/join/exchange` | Untrusted guest redeems a bearer write code for a write cap |
| daemon (loopback) → webserver in-process | Grant registration / RW-gate state set by the owner's own daemon |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-171-01 | Elevation of Privilege | `handleWSSRelay` write path (MsgInput/MsgSessionInject) | critical | mitigate | Grant-gating (D-01): a write cap whose grant is not registered fails `isGrantActive` at WS upgrade → 403. Proven by TestHandleWSSRelay_WriteCap_RequiresGate through the real upgrade path (NOT an originAllowedForWrite unit test — Pitfall 1). |
| T-171-02 | Elevation of Privilege | RW teardown via `ClearGrants` | high | mitigate | New surgical `RemoveGrant(sessionID, grantID)` removes only the RW grant; reusing `ClearGrants` would also wipe the tailnet read/write grants (Pitfall 2). Test asserts sibling grants survive. |
| T-171-03 | Tampering | Concurrent redeem of the single-use write code | high | mitigate | `Exchange`'s single-mutex atomic lookup+delete is unchanged; `IssueSingleUseWithTTL` sets `reusable:false` so exactly one redeemer wins (R2). |
| T-171-04 | Denial of "share must end" | Custom-TTL write code silently truncated to 5m | medium | mitigate | `IssueSingleUseWithTTL` uses the caller-supplied ttl, not the manager's fixed field (Pitfall 4). |
| T-171-05 | Spoofing / Tampering | files.write over spoofed/Funnel origin for a non-gated session | medium | mitigate | Gate-aware `originAllowedForWrite` (D-02) rejects funnel-origin writes unless `isRWGated`; defense-in-depth for the files.write routes (the gate cap never carries files.write — D-05). |
