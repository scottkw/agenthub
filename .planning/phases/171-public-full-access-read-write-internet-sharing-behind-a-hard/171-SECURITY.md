# Phase 171 Security: Closed Write Perimeter for Public Full-Access (RW) Sharing

**Scope:** FNL-09 — opt-in public read-write terminal access over Tailscale Funnel, gated behind a hard 3-second hold-to-confirm consent affordance and a single-use write code. This document is the SPEC R8 deliverable: a synthesized, standalone threat model for the whole phase (Plans 171-01 through 171-04), reconciled against the implemented code, asserting the closed write perimeter.

---

## 1. The Load-Bearing Invariant

**Invariant: no public write path exists except through the new hard consent gate.**

Before this phase, `issueCapabilitiesForSession` shared a single `base` URL variable between the read and write capability links; when Funnel was active, both silently rebased to the public Funnel base URL, and the Funnel proxy exposed the entire session mux with no read-only downgrade. The result was an **accidental** public write path — internet-reachable command execution with no consent step of any kind (T-171-07 below). This phase's entire purpose is to close that path and replace it with exactly one, deliberate, revocable, single-use public write grant.

### 1.1 Enforcement mechanics — the primary barrier

The write path an attacker actually cares about is the one that reaches the PTY: `MsgInput` and `MsgSessionInject` frames over the real `GET /sessions/{id}/ws` relay upgrade. The enforcement point that gates that path is **grant-registration gating (D-01)**:

- `requireCapability`'s `isGrantActive(sessionID, grantID)` check at the WS upgrade is the primary and **sufficient** terminal-write barrier. A capability token with `Perms` containing `write` is cryptographically valid (correct HMAC, unexpired) but is REJECTED at upgrade (403/401) unless its grant is separately registered via `ws.AddGrant`.
- The write grant is registered **only** by the gate handler (`handleSetSessionFunnelWrite`, `POST /sessions/{id}/funnel-write`), and only as one atomic post-hold action: `ws.AddGrant(...)` + `ws.SetRWGate(sessionID, true)` + `joinCodes.IssueSingleUseWithTTL(...)`. There is no other code path in the daemon or webserver that calls `ws.AddGrant` for a Funnel-origin write capability.
- Teardown is symmetric and surgical: `WebServer.RemoveGrant(sessionID, grantID)` removes exactly the one write grant (never `ClearGrants`, which would also wipe the session's unrelated tailnet read/write grants — T-171-02). `revokeFunnelWriteLocked` is the single shared sub-teardown primitive that calls it, invoked from both the RW-only `DELETE /sessions/{id}/funnel-write` disable path and appended inside `disableFunnelForSession`'s existing four-trigger cascade (funnel-off, web-share-off, session-exit, auto-expiry).
- This is proven at the real enforcement boundary — not by proxy — by `TestHandleWSSRelay_WriteCap_RequiresGate`: a write-permission capability whose grant is unregistered is rejected at the actual `GET /sessions/{id}/ws` upgrade handler; once `AddGrant` registers it, the identical token both completes the upgrade and reaches the PTY as a genuine writer.

### 1.2 `originAllowedForWrite` (D-02) — defense-in-depth, explicitly secondary, and explicitly NOT sufficient alone

`originAllowedForWrite` gained a gate check (`isRWGated(sessionID)`) on its Funnel-origin branch in 171-01 (T-171-05). This function is **defense-in-depth for the `files.write` HTTP routes only** (its sole call site is `requireFilesWrite`). It does **not** reach `MsgInput` or `MsgSessionInject` — those frames flow through the WS relay's read pump, which is gated exclusively by `isGrantActive` at upgrade (Section 1.1), not by `originAllowedForWrite`. The function's stale doc-comment (which previously and incorrectly implied it covered the terminal-write path) was corrected in 171-01 specifically to prevent this class of misreading. Treating `originAllowedForWrite` as the terminal-write barrier would be a security-relevant documentation error — Pitfall 1 in the 171-01 RESEARCH/plan — and this document explicitly does not make that error: it is a secondary barrier narrowing an already-narrow HTTP surface (`files.write`), never the primary barrier for command execution.

### 1.3 Scope narrowing: terminal-only, never `files.write`

Independent of the gating mechanics above, the gate-minted write capability itself is scoped to be incapable of reaching `files.write` at all: `handleSetSessionFunnelWrite`'s `Perms` field is hardcoded to `"read,write"` (the terminal read/write permission set) and the handler never calls `browseEnabledFor` — so the minted capability cannot carry `files.write` permission regardless of the session's browse toggle (T-171-06). Public write access is command execution via the terminal only; public remote file editing/upload was explicitly out of scope for this phase (SPEC Boundaries).

## 3. Trust Boundary Provenance: the loopback funnel-write endpoint

`POST /sessions/{id}/funnel-write` (the gate-mint handler) and `DELETE /sessions/{id}/funnel-write` (the RW-only disable handler) are registered on the daemon's **loopback-only, owner-authenticated mux** — the same trust boundary already established for the existing Phase 165/170 Funnel-toggle loopback endpoints (`POST /sessions/{id}/funnel`, the read-Funnel enable/disable path). This is **inherited enforcement, not a newly assumed boundary**: the loopback socket is reachable only by processes running as the local owner (the daemon's Unix domain socket / named pipe, never guest-reachable over any network interface), exactly mirroring the precedent set by `ToggleWebServing`, `SetSessionFunnel`, and `DisconnectViewers` (T-168-07). No new "owner-only, no auth" assumption was introduced by this phase — the write-gate endpoints simply reuse the daemon's one existing owner-trust boundary.
