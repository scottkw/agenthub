**Deliberate exclusion:** `--hub-warning` (`#fbbf24` / `#b45309`, used by the read-side risk panel's `⚠` icon and left-border) is intentionally NOT reused here. The Danger section uses `--hub-destructive` throughout instead — a distinct hue from the read panel's amber, reinforcing (never solely carrying) the fact that this is a different, more severe grant. This is the "color as reinforcement, never sole signal" pattern: even a colorblind reader gets the real distinction from the **heading text**, **section title**, **icon** (`LockOpenIcon` vs `GlobeAltIcon`/`ExclamationTriangleIcon`), and **shape** (notched badge vs pill, 2px destructive top-border vs 1px neutral border) — color is never asked to carry the distinction alone.

### New tokens — FULL ACCESS badge (public write indicator)

Add these to the dark and light `:root` blocks in `style.css`, adjacent to the existing `--hub-internet-badge-*` pair (line ~4707/4766).

**Dark mode additions:**
```css
/* COLORBLIND-SAFE: full-access badge dark hex = --hub-destructive (#f7768e) — reinforcement
   only; LockOpenIcon shape + "FULL ACCESS" text + notched badge geometry carry the state.
   Deliberately a DIFFERENT hue from --hub-internet-badge-text (#43ddb2 teal) so the two
   badges are never confusable even in a side-by-side grayscale render. */
--hub-fullaccess-badge-bg: rgba(247, 118, 142, 0.15);
--hub-fullaccess-badge-text: #f7768e;
```

**Light mode additions** (inside `[data-ui-theme="light"]` block):
```css
/* COLORBLIND-SAFE: full-access badge light hex = --hub-destructive (#c0394f) — WCAG AA
   verified 4.7:1 on #ffffff (same token already verified at style.css:4728). Reinforcement
   only; icon + text + shape carry the state. */
--hub-fullaccess-badge-bg: rgba(192, 57, 79, 0.13);
--hub-fullaccess-badge-text: #c0394f;
```

**Colorblind-safety verification (MANDATORY per standing convention — user is colorblind):**
- State is encoded by **three independent non-color axes**, all required by R7 and D-09:
  1. **Text label:** "FULL ACCESS" (read badge says "INTERNET" — different word, not different color of the same word)
  2. **Icon:** `LockOpenIcon` (read badge uses `GlobeAltIcon`) — different silhouette, verifiable in the import statement and in a grayscale render
  3. **Shape:** notched/angled-corner geometry via `clip-path` (read badge is a uniform `border-radius: var(--hub-radius-pill)` rounded pill) — verifiable by inspecting the CSS rule, not by eye
- Color (`--hub-fullaccess-badge-text`) is reinforcement only. Deleting the color entirely (e.g. forcing both badges to `currentColor`) must not remove the ability to tell them apart — label + icon + shape alone must still disambiguate.
- Contrast: dark `#f7768e` on `#14151b` bg ≈ 7.3:1 AA PASS. Light `#c0394f` on `#f5f5f7` ≈ 4.7:1 AA PASS (same token, already verified at `style.css:4728`).
- **Verification method:** grep for `hub-fullaccess-badge-text` and `hub-internet-badge-text` and confirm they resolve to different hex constants in both theme blocks; grep the badge component files for two different icon import names (`LockOpenIcon` vs `GlobeAltIcon`) and two different literal label strings (`"FULL ACCESS"` vs `"INTERNET"`); confirm the `.hub-fullaccess-badge` CSS rule uses `clip-path` (not `border-radius: var(--hub-radius-pill)`). Do this at the source level — never by rendering and eyeballing.

## Interaction Contract

### Gate visibility vs. Funnel warm-up state (RESEARCH.md Open Question 1 — resolved)

The Danger section (`.hub-funnel-write-gate`) renders whenever `funnelEngaged` is true (warming up, warm-up-timed-out, or active) — same gating as the read section, so the two sections always appear/disappear together as a visual pair. **However, the hold-to-confirm control itself is `disabled` (HTML `disabled` + `aria-disabled="true"`) until `funnelActive && !warmingUp`.** Rationale: the RW cap's URL is meaningless before the Funnel base URL exists; a hold-to-confirm that "succeeds" into nothing is a worse UX than a visibly-disabled control with an explanatory note ("Waiting for internet share to finish starting up…", 12.5px / `--hub-text-muted`, same tone as the read section's warm-up message).

### Hold-to-confirm gate flow (D-01, D-07, R1)

```
State machine:
  idle (gate not held) → [pointerdown on hold-btn, ≥3s elapsed] → gate-complete → active
                        → [pointerup/pointerleave before 3s]    → idle (bar resets to 0%, nothing issued)
  active (writer not yet redeemed) → [countdown reaches 0 OR owner clicks Disable] → idle
  active → [guest redeems write code] → used (one writer connected)
  used → [countdown reaches 0 OR owner clicks Disable] → idle
```

1. **Idle:** `.hub-funnel-write-gate__hold-btn` shows fill at 0%, label "Hold 3s to confirm". No write cap, no write grant, no write code exist yet — `SetSessionFunnelWrite` has not been called.
2. **Holding (`pointerdown`):** fill animates left→right from 0% to 100% over exactly 3000ms (linear). Label switches to "Holding… keep pressing". This is the ONLY interaction affordance in this phase driven by continuous motion — see Motion below for the reduced-motion adaptation, which preserves the geometry cue without smooth easing.
3. **Early release (`pointerup`/`pointerleave` before 3000ms elapses):** fill resets instantly to 0%, label reverts to "Hold 3s to confirm". **No API call is made.** No write URL, code, or grant is issued (R1 acceptance criterion — verify via a test that asserts zero `SetSessionFunnelWrite` calls on early release).
4. **Hold completes (3000ms reached while still pressed):** exactly one call to `SetSessionFunnelWrite(sessionId, expirySeconds)` fires. Fill stays at 100% momentarily (visual confirmation) then the control is replaced by `.hub-funnel-write-gate__result`.
5. **Active (post-gate, unredeemed):** `.hub-funnel-write-gate__result` shows the public write URL (Copy/Open/QR row, mirrors the read section's URL row), `<CodeDisplay label="Single-use write code:" code={writeCode} />`, a live countdown ("Expires in mm:ss"), and the `.hub-funnel-write-gate__disable` button.
6. **Guest redeems the code:** on the next session-info poll (client detects the write cap has been consumed — see RESEARCH.md's client-side `expiresAt` + poll-confirmed-flip pattern), the URL/code rows collapse and `.hub-funnel-write-gate__used` renders: "Write code used — one writer connected" (12.5px / 600 / `--hub-text-secondary`), countdown continues, disable button remains available.
7. **Disable (owner clicks "Disable public write" at any point in Active or Used):** single click, no secondary confirmation dialog (the hold-to-confirm gesture WAS the confirmation, on the way in — an extra confirm-to-disable would be inconsistent asymmetry). Immediately calls the RW-disable RPC; on response, collapse back to Idle. Read section is unaffected (SPEC prohibition — verify via a test that the read code/badge survive an RW-only disable).
8. **Expiry (countdown reaches 0, no owner action):** identical end-state to Disable — collapse to Idle, badge clears, next writer request 401s. Auto-detected via the poll-confirmed `funnelWriteActive` flip (same mechanism as read-share auto-expiry today).
9. **Re-share:** from Idle, the owner must hold the gate again (3s) to re-issue — there is no "re-send the same code" affordance (SPEC: single-use, re-share requires re-gating).

### Expiry selector (D-11, R5)

`<select>` element inside the Danger section, visible from Idle state onward (so the owner picks duration before or during the hold — selecting mid-hold is fine since nothing is committed until 3s completes).

| Display label | Value passed to `SetSessionFunnelWrite` (expirySeconds) |
|---------------|-----------------------------------------------------------|
| 15 minutes (default) | 900 |
| 30 minutes | 1800 |
| 1 hour | 3600 |

No "Until I disable" option exists for RW (unlike the read panel's read-share selector) — this is a deliberate, structural difference from `.hub-funnel-risk-panel__expiry`'s five-option set, itself part of the "never confusable with the read flow" contract. Selecting nothing defaults to 15 minutes. The 1-hour hard clamp is additionally enforced server-side per R5 (`ExpiresIn == 0 || > 3600` → effective 3600) — the UI-SPEC records this as context for the countdown's max value, not as a UI task (server-side clamp is a backend concern, out of this document's scope).

### Focus management

- The hold-to-confirm control is reachable via Tab, and is a real `<button>` (not a `<div>` with a click handler) so it is natively focusable and operable via keyboard: `keydown`/`keyup` on Space or Enter drives the same 3000ms hold timer as `pointerdown`/`pointerup` (releasing the key early = early release; this is a hard accessibility requirement — a press-and-hold gesture MUST have a keyboard equivalent, not just pointer events).
- Tab order within the Danger section: expiry select → hold-to-confirm button → (once active) Copy → Open → QR → Disable.
- On successful gate completion, focus moves to the "Disable public write" button (the new most-relevant destructive action, mirroring how the read panel returns focus to its toggle after commit).
- `:focus-visible` outline: `2px solid var(--hub-accent)` (unchanged focus-ring color — focus rings stay accent-blue everywhere in the app; only the Danger section's *content* avoids accent, not its focus affordances).

### Motion

The hold-bar fill IS the primary feedback mechanism (D-07) — unlike the Phase 166 risk panel's purely decorative expand/collapse, this motion is functionally load-bearing (it communicates elapsed hold time). It is therefore NOT fully disabled under `prefers-reduced-motion: reduce`; instead it degrades to discrete, non-eased steps so the geometry cue survives:

```css
@media (prefers-reduced-motion: no-preference) {
  .hub-funnel-write-gate__hold-fill { transition: width 50ms linear; }
}
@media (prefers-reduced-motion: reduce) {
  /* Geometry-based feedback (the fill width itself) is functional, not decorative,
     so it is NOT suppressed — only the smoothing easing is removed. The fill still
     advances in discrete steps (e.g. every 150ms) so a reduced-motion user still
     gets the ≥3s hold confirmation via width, just without continuous animation. */
  .hub-funnel-write-gate__hold-fill { transition: none; }
}
```

All other new motion (Danger section reveal alongside the existing `funnelEngaged` conditional render) has no dedicated transition — it appears/disappears with the rest of the Internet section block, inheriting whatever the existing `.hub-share-internet-section` mount/unmount behavior already is (no animation today).

### Destructive actions

| Action | Confirmation approach |
|--------|-------------------------|
| Enable public write (the gate itself) | The 3-second hold-to-confirm gesture IS the confirmation mechanism (R1) — no additional modal/dialog. This is the phase's single highest-stakes affordance in the whole app; the hold gesture is deliberately friction-heavy (slow, effortful, abortable) rather than a single click + separate confirm dialog, per D-01/D-07/D-08's combined intent. |
| Disable public write | Single click, no secondary confirmation — asymmetric with the enable gate (getting IN is hard, getting OUT is easy) by design: an easy disable encourages owners to actually use it when the writer is done, rather than leaving a live RCE grant open because disabling feels burdensome. |

### Copy compliance check (against SPEC's Prohibition #4)

> "The consent-gate copy MUST NOT understate the grant — it must state 'command execution' and 'anyone with the link' and must not use softened/euphemistic wording."

The locked warning body copy contains both required phrases verbatim: **"command execution"** and **"anyone with the link"**. This is a hard pass/fail check the checker/executor must re-verify against the literal implemented string, not a paraphrase.
