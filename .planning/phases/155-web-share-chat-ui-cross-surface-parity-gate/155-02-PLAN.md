<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| web-share browser → webserver WS/REST | The `?cap=` token is the only authorization credential; the client forwards it opaquely and never decodes it |
| read-only cap holder → chat send / @session inject | The client UI must not present an authoritative gate; the server is the gate |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-155-01 | Elevation of Privilege | ChatPanel Send / inject under a RO cap | high | mitigate | Server-side gate is authoritative and unchanged (HandleChatSend/HandleInject bound to signed JWT claim). This plan adds client-side suppression (disable Send, short-circuit inject, RO label) derived from the server's `/info` perms — defense-in-depth only. The adversarial server-gate proof is the e2e in Plan 155-04. |
| T-155-06 | Tampering / Spoofing | client handling of the cap JWT | medium | mitigate | Client never JWT-decodes the cap; RO status is read from the server's `/api/sessions/{id}/info` perms response. The cap is forwarded opaquely as `?cap=${encodeURIComponent(token)}`. |
| T-155-05 | Information Disclosure | cap token in WS/REST URL | low | accept | Cap tokens in `?cap=` appear in browser history; this is the existing production pattern (time-bounded JWTs). No change. |
| T-155-SC | Tampering | npm/pip/cargo installs | n/a | accept | No new packages (RESEARCH: New npm packages: NONE). Executor must confirm no `rehype-raw`-style raw-HTML plugin is added to any new import (inherited SEC-03). |
</threat_model>
