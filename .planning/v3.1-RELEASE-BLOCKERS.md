# v3.1 Release Blockers

This document tracks bugs and follow-ups identified during v3.1 UAT (Phases 88 + 89 + 90 Plan 06). Each item is classified as **BLOCKER** (must fix before tagging v3.1.0) or **POLISH** (can ship as-is, schedule for v3.1.1 or v3.2).

## Blockers (must fix before v3.1.0)

### ~~B-1. Native session pane renders blank in AgentHub GUI~~ ✅ FIXED in `b9f3176` (take 1) + `84f0ae1` (take 2)

**Severity:** Critical — core functionality regression.

**Symptom:** Session tabs in the AgentHub desktop window show an empty terminal pane. The session itself is alive (the agent process runs, web-served instances render correctly with live PTY echo), but the in-app xterm.js panel is empty.

**Discovered during:** Phase 88 Item 1 UAT (2026-05-02). User opened a Claude Code session, the native tab was blank, but the same session displayed correctly when accessed via the web URL on Safari.

**Root cause:** Phase 88's Origin allowlist on the relay (`internal/relay/server.go:loopbackOriginPatterns`) only permitted `http(s)://localhost:<port>` and `http(s)://127.0.0.1:<port>`. The Wails desktop webview emits Origin `wails://wails.localhost` (no port in production, or with Vite HMR port in dev), which didn't match any pattern. coder/websocket's `authenticateOrigin` rejected with 403, manifesting in the browser console as "WebSocket is closed before the connection is established" / "There was a bad response from the server". xterm mounted but had nothing to write.

**Fix (take 1, `b9f3176`):** Added Wails origin patterns to the allowlist (`wails://wails.localhost`, `wails://wails.localhost:*`, `http://wails.localhost`, `http://wails.localhost:*`). Verified against `wails dev` — all 4 agent CLIs rendered live PTY output.

**Regression on rc4 production binary:** The `wails dev` test was a false-positive. `wails dev` uses Wails CLI v2.10.2 in dev mode, which emits Origin `wails://wails.localhost:34115`. The rc4 production binary (built against pinned wails v2.12.0) emits Origin `wails://wails` — a bare host with no `.localhost` suffix. Per Wails v2.12.0 source (`internal/frontend/desktop/darwin/frontend.go:40`), production startURL is `wails://wails/`; the `.localhost` suffix is only appended in dev mode (line 109).

**Fix (take 2, `84f0ae1`):** Replaced the `wails://wails.localhost` pattern with `wails://wails` (bare host) for production macOS/Linux. Kept the dev-mode and Windows patterns. Two new tests target both production-darwin and production-windows origins explicitly. Verified against rc5 production-binary install: all sessions render correctly.

**Lesson:** Don't use dev-mode behaviour as a proxy for production correctness when the framework's URL scheme differs between modes.

**Confirms the trigger matrix question:** affects ALL native sessions regardless of web-enabled / Tailscale state — the relay path is the same for all. The original "blank when web-enabled in LAN mode" framing was wrong.

## Polish / follow-up findings (non-blocking)

### P-1. AgentHub doesn't auto-detect Tailscale daemon coming back online

After `sudo launchctl load com.tailscale.tailscaled.plist` + `sudo tailscale up`, the Settings panel shows Tailscale as Connected but the web server URL stays bound to the LAN IP. Manual Stop/Start Web Server is required to force re-binding. Worth a state-change watcher in the Tailscale-mode detector.

**Discovered:** Phase 88 Item 2 UAT.

### P-2. QR code in Sessions tab doesn't refresh after JoinCodeManager state is wiped

When the web server restarts (e.g., during a manual mode switch), in-memory join codes are invalidated, but the displayed QR continues to encode the old, now-invalid code. First scan returns "expired"; "Stop sharing / reshare" issues a fresh code. Should refresh QR (or invalidate the share UI) on web-server-restart events.

**Discovered:** Phase 88 Item 2 UAT.

### P-3. Sessions panel doesn't show LAN Basic Auth password (only Settings does)

When the user lands on the Sessions panel after enabling local-network mode, there's no inline reminder of the Basic Auth password — it's only visible in Settings. For a fresh user who hasn't been to Settings yet, this is a discoverability gap.

**Discovered:** Phase 89 UAT (2026-05-02, before this session's work — recorded in original HANDOFF.md).

### P-4. Safari rejects self-signed cert exceptions for subresources in LAN-fallback mode

Per the prior Phase 89 UAT note: Safari accepts the cert for the main page but re-prompts (or silently blocks) when subresources hit the same self-signed origin. The xterm.js subresource loads worked in this session's UAT against rc3, but worth documenting as a known Safari quirk.

**Discovered:** Phase 89 UAT.

### P-5. UAT-2 doc references `agenthub start` — not a real command

Phase 89 HUMAN-UAT.md instructs `agenthub start`, but the correct invocation is `open -a AgentHub` (GUI) or running `agenthub` with no arguments (which dispatches to GUI mode per the unified entrypoint). Doc-only fix.

**Discovered:** Phase 89 UAT.

### P-6. Launching AgentHub via Finder / `open` causes share URLs not to appear

Launching from the terminal works; launching via Finder produces sessions whose share URLs never surface in the UI. Likely environment-variable inheritance issue (PATH? HOME?). Phase 87 follow-up.

**Discovered:** Phase 89 UAT.

### P-7. publish glob too broad — fixed in main (6ad9bef), unverified by run

The release.yml publish step's `artifacts/*.tar.gz` glob caused the unsigned `AgentHub.app.tar.gz` intermediate to leak into the v3.1.0-rc3 draft release alongside the version-prefixed Linux tarball. Tightened to `artifacts/agenthub-*.tar.gz` in commit `6ad9bef`. Will be verified on the next release.yml run.

**Discovered:** Phase 90 Plan 06 step 9 UAT.
