## Polish / follow-up findings (non-blocking)

### P-1. Phase 95 — `mailto:` URLs not detected as clickable links

**Severity:** Major (documented spec gap; not a security regression)

**Symptom:** Print `mailto:noreply@example.com` into a terminal with the Web Links plugin ON. The URL renders as plain text with no underline, no hover tooltip, and Cmd-click does nothing. The other allowlisted schemes (`https`, `http`) and disallowed schemes (`javascript:`, `ftp://`) all behave correctly.

**Discovered during:** Phase 95 LNK-02 UAT, 2026-05-11. Fixture `/tmp/web-links-test.sh` exercised five URL forms; only mailto failed.

**Spec reference:** Phase 95 documents the scheme allowlist as `https`, `http`, `mailto` (95-VERIFICATION.md and 95-DESKTOP-UAT.md §2 / LNK-02). Implementation honors https + http but not mailto.

**Suggested fix:** Audit the web-links addon's URL regex / scheme handler in `frontend/src/components/TerminalPanel.tsx` (LinkConfirmPopover wiring) and `web/assets/terminal.js`. Determine whether mailto matching is configured at the addon level or filtered upstream. If the addon doesn't natively match mailto, add a custom matcher per addon docs.

### P-2. Phase 95 — Cyrillic IDN spoof URLs not detected as links

**Severity:** Major (security-relevant spec divergence; defensive-by-accident)

**Symptom:** Print `https://gооgle.com` (two `о` are Cyrillic U+043E, not Latin) into a terminal. The URL renders as plain text — no underline, no hover tooltip, no Cmd-click action. Spec (LNK-03 / SC-3) expects detection AS a link followed by an IDN/spoof confirmation popover with the resolved (Punycode) URL and Continue/Cancel buttons.

**Discovered during:** Phase 95 LNK-03 UAT, 2026-05-11.

**Two interpretations to reconcile:**

1. **Bug** — the URL regex doesn't admit non-ASCII hostname characters, so any IDN URL silently passes through as inert text.
2. **Feature** — the addon defensively filters non-ASCII hostnames as an anti-spoof measure, making the popover unreachable.

Either way, the spec mandates the popover (user education), not silent rejection. If interpretation (2) is intended, the spec should be updated to reflect "non-ASCII hostnames are dropped entirely; no popover".

**Security posture:** Defensive-by-accident — a user cannot inadvertently Cmd-click a homograph URL. So the **risk is low** even with the bug present. The fix is primarily about meeting the documented spec and educating users about IDN-based phishing.

**Suggested fix:** Inspect the addon URL matcher to understand its hostname character class. If extending to admit non-ASCII chars, ensure the IDN/Punycode confirmation flow (LinkConfirmPopover with `getRisk(displayUri, resolvedUri)`) fires for ANY URL whose Punycode form differs from its display form.

### P-3. Phase 94 — Find bar will not dismiss after clicking the case-sensitive toggle

**Severity:** Major (usability blocker for the affected interaction sequence; workaround = restart app)

**Symptom:** Open the find bar (Cmd-F). Click the **case-sensitive** toggle in the bar. Try to close the bar with **Esc** or the **close button** — neither dismisses the bar. (Compare: before toggling, both Esc and close button dismiss the bar instantly — see P-4 for the missing exit animation. After the toggle click, neither works at all.)

**Discovered during:** Phase 94 UAT-2, 2026-05-11. Not on the existing WR-01/WR-02 list.

**Hypothesis:** The toggle's click handler probably steals/changes focus into the toggle's button element, and the keyhandler that listens for Esc is scoped to the search input (which is no longer focused). The close-button regression is harder to explain from focus alone — possibly an event-propagation issue introduced alongside the toggle interaction.

**Suggested fix:** Reproduce, then add a passive listener at the find-bar root for Esc / close events so the dismiss is not focus-dependent, OR re-focus the search input after a toggle click.

### P-4. Phase 94 — Find bar slide-out animation missing on Esc / close

**Severity:** Minor (cosmetic; half of WR-01 reproduced)

**Symptom:** Cmd-F slide-IN works correctly (~200ms slide-down with the .find-bar--entering class). But Esc and the close button cause the bar to disappear **instantly** with no exit transition. The .find-bar--exiting class is never applied during close.

**Discovered during:** Phase 94 UAT-1, 2026-05-11.

**Suggested fix:** Per the existing WR-01 gap analysis in 94-VERIFICATION.md, apply `.find-bar--exiting` on close with a 150–200ms delayed unmount in `FindBar.tsx`. Mirror the same in `web/assets/terminal.js` `hideFindBar()`. The transition CSS rule already exists in `style.css:2176-2184` — it's currently dead code.

### P-5. Phase 96 — iTerm2 inline-image protocol (IIP / OSC 1337) not rendering

**Severity:** Side observation (sixel works; phase verification tables test sixel, not IIP)

**Symptom:** With the Image plugin ON, sixel sequences render correctly in a fresh tab. iTerm2 IIP sequences (`ESC ] 1337 ; File = name=...;inline=1 : base64 BEL`) produce no rendered image — the escape is silently consumed (no garbage text) but no image appears.

**Discovered during:** Phase 96 Scenario 3 UAT, 2026-05-11. Fixture `/tmp/image-test.sh` tested both protocols side-by-side; only sixel rendered.

**Three possibilities:**

1. `ImageAddon` construction in `TerminalPanel.tsx:235` passes only `storageLimit` and `enableSizeReports`. The `iipSupport` option is not set. Per `@xterm/addon-image` docs it defaults to `true`, but it's worth confirming the docs match the vendored bundle's actual default.
2. Fixture's IIP escape syntax was rejected by a strict parser (the `name=` value should arguably be base64-encoded per the iTerm2 spec; my second-pass fixture switched to a properly base64-encoded `name=cmVkYm94LnBuZw==` and still didn't render — so a syntax issue can't be definitively excluded but seems unlikely).
3. v3.2 intentionally ships sixel-only and the docs' "iTerm2 IIP supported" advertisement is aspirational.

**Suggested action:** Confirm intent. If IIP is supposed to work in v3.2, add an integration test or audit the addon construction. If sixel-only is intentional, update Phase 96 SUMMARY and the addon-image vendor README so users know which protocols are supported.
